# План реализации payplump-bot

Основа — [spec.md](spec.md). Бизнес-правила определяет ТЗ, этот файл задаёт
порядок работы и отслеживает её выполнение. Исходное состояние сверено с
`main` на коммите `d57d625` от 17 октября 2026 года.

## Как вести план

- `[ ]` — работа ещё не завершена; `[x]` — выполнена и проверена.
- Реализацию отмечаем после проверок и слияния соответствующего PR.
  Испытания на установленном сервисе или VPS отмечаем только после их проведения.
- В PR указываем пункты этого плана и обновляем их состояние. Для внешних
  испытаний сохраняем результат, версии сервисов и условия проверки без секретов.
- Изменения делаем небольшими коммитами в отдельных ветках, через PR для ревью
  владельца. Напрямую в `main` не пушим; самостоятельно PR не сливаем.
  Один этап может состоять из нескольких небольших PR.
- Новые сведения об API уточняют технические шаги; изменения бизнес-правил
  отражаем также в `spec.md`. Рабочие секреты не помещаем в Git или этот файл.

- [x] Атомарная регистрация в слое хранения: один клиент, одна подписка без доступа и одно долговечное задание.
- [x] Тесты конкурентной регистрации, повторного обращения и отката при ошибке записи задания.
- [x] Календарные функции: таймзона сервера с fallback на UTC, полночь после дня оплаты, следующий месяц от даты платежа с ограничением последним днём.
- [x] Тесты календарных границ, високосного года, переходов DST и недоступной таймзоны.
- [x] Подготовлены CI с GitHub Variables / Secret `PGPASSWORD`, интеграционные тесты и smoke-проверка бинарника.
- [x] Подготовлены и локально проверены статическая сборка, Distroless-образ по digest, nonroot, exec-healthcheck и Compose для разработки.
- [x] Документированы локальный запуск и настройки PostgreSQL; в CI и Compose заменён `trust` на SCRAM-SHA-256.
- [ ] Подтвердить успешный GitHub Actions run после заполнения Variables и Secret в настройках репозитория; сохранить ссылку на запуск.

Эти галочки относятся к основе сервиса. Telegram, Invoice Ninja и S-UI ещё
не подключены; полный платёжный цикл и готовность рабочего развёртывания не проверены.

## 1. Telegram: приём личного `/start` — следующий PR

Можно реализовать независимо от доступности Invoice Ninja и S-UI.

Реализация подготовлена в ветке `feat/telegram-start`: локально проверяются
API-клиент на тестовом HTTP-сервере, транзакции на PostgreSQL и жизненный цикл
polling. Пункты ниже остаются неотмеченными до ревью и слияния PR согласно
правилам плана. Проверка настоящего бота относится к настройке тестовой
интеграции в этапе 2; ответы и меню — к этапам 3–5.

- [ ] Добавить конфигурацию токена Telegram и список Telegram ID администраторов через окружение, без вывода секретов в лог.
- [ ] Реализовать клиент Telegram Bot API: проверку ответов, таймауты, обработку ошибок и `retry_after`.
- [ ] Добавить long polling и корректную отмену запросов при остановке процесса.
- [ ] Долговечно хранить обработку updates / offset: подтверждать update после фиксации результата в PostgreSQL.
- [ ] Принимать `/start` только из личного чата, использовать ID отправителя для идентификации и существующую транзакционную регистрацию.
- [ ] Повторный `/start` открывает существующую запись; повтор одного update не создаёт новых заданий или повторной бизнес-обработки.
- [ ] Проверить разбор updates, групповые сообщения, повторную доставку, ошибки БД и перезапуск между получением и подтверждением update.

## 3. Долговечные задания, события и исходящие сообщения

Слой хранения уже записывает `register_client`, но исполнитель ещё отсутствует.

- [ ] Добавить миграции для `processed_events`, `outbox` и необходимых полей операций / подписок, сохраняя уже применённые миграции.
- [ ] Реализовать выборку заданий порциями, блокировку, срок аренды, число попыток, отложенные повторы и восстановление незавершённой работы.
- [ ] Раздельно хранить желаемое состояние доступа и результаты шагов Invoice Ninja, S-UI и Telegram.
- [ ] Записывать изменение бизнес-состояния, новые операции и уведомления атомарно; сериализовать обработку по клиенту.
- [ ] Добавить outbox-доставку с таймаутами и учётом `retry_after`; ошибка одного адресата не останавливает остальных.
- [ ] Перед повтором создания объекта во внешней системе восстанавливать результат предыдущего запроса по сохранённым идентификаторам / соответствиям.
- [ ] Проверить конкуренцию исполнителей, истечение аренды, падение после внешнего успеха и повтор только незавершённых шагов.

Outbox защищает бизнес-обработку от повторов, но при сетевом сбое с неизвестным
результатом абсолютная гарантия ровно одного Telegram-сообщения не обещается.

- [ ] Создавать один обычный счёт с выбранным продуктом, переводить его в выставленное состояние и задавать срок оплаты в день выставления.
- [ ] Сохранять ID счёта; брать номер, сумму и ссылку из конкретного счёта, без локально заданной цены.
- [ ] Через outbox уведомлять клиента о сумме, реквизитах и сроке, администратора — о регистрации и счёте.

- [ ] Защитить обработку от повторных и запоздалых событий; один оплаченный период не продлевается дважды.
