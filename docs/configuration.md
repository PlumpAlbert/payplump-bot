# Конфигурация обычного запуска

При обычном запуске работают все основные функции: Telegram, регистрация,
проверка первой оплаты, создание recurring, выдача конфигурации и наблюдение
существующих клиентов и счетов. [Ninja определяет состояние](ninja-authority.md);
бот создаёт отсутствующий S-UI, но никогда не меняет существующий.
Администратору доступны команды рассылки, но каждая отправка требует
предпросмотра и подтверждения. Запуск приложения сам ничего не рассылает.

## Что заполнять

[`.env.example`](../.env.example) содержит подключения и бизнес-параметры:

- PostgreSQL через `DATABASE_URL` либо `PGHOST`/`PGUSER`/`PGDATABASE` и остальные
  необходимые параметры выбранного способа подключения.
- Токен Telegram и ID администраторов. По умолчанию используется long polling;
  URL и секрет Telegram webhook нужны только при выборе webhook.
- URL/token Invoice Ninja и API ID продукта (не его название/артикул).
  Налоговый режим при необходимости переопределяется явно; по умолчанию читается
  из настроек компании Ninja. Поле Telegram ID по умолчанию `id_number`.
  Секреты webhook необязательны; для обоих можно указать одно значение.
- URL/token S-UI, выбранные inbounds и публичную HTTPS-базу URL подписки.
- `PAYMENTS_CURRENCY_ID`: внутренний ID родной валюты Ninja;
  `PAYMENTS_CURRENCY_CODE`: соответствующий трёхбуквенный ISO-код, например `USD`.
  Оба параметра необязательны: бот читает валюту компании через выбранный продукт
  (`include=company`), а её ISO-код из `GET /api/v1/statics`. Явные значения имеют
  приоритет. Это одна общая настройка для платежей и импорта, не отдельный тариф.
  Если API не предоставляет эти поля, ошибка называет недостающее поле и параметр
  для ручной настройки; случайная валюта клиента не подставляется.
- Телефон для оплаты, при необходимости банк и получателя.
- `TZ`: явную расчётную таймзону, например `UTC` или `Europe/Moscow`.

Поле Telegram ID по умолчанию `id_number`; текущий профиль записи поддерживает
именно его. Номер релиза Ninja/S-UI не является условием запуска или разрешением
на API-операцию. `INVOICE_NINJA_VERSION` и `SUI_VERSION` больше не нужны;
оставленные старые значения не блокируют запуск. Проверяются реальные поля
ответов, принадлежность счетов, валюта и суммы. Webhook доступен как второй
вариант транспорта Telegram. Пустой секрет Ninja/lifecycle отключает только
соответствующий HTTP-маршрут; опрос API продолжает работать.

> [!WARNING]
> **Webhook Invoice Ninja не настроен автоматически.** Бот требует для обоих
> маршрутов заголовок `X-Payplump-Webhook-Secret` с настроенным значением секрета.
> Это требование бота, а не встроенная подпись или стандарт Invoice Ninja 5.13.47;
> возможность задать произвольный заголовок в его интерфейсе не подтверждена.
> Если используется посредник, он должен сначала надёжно удостовериться в
> источнике запроса; нельзя безусловно добавлять секрет ко всем запросам.
> Доставка webhook и механизм проверки отправителя ещё не проверены в рабочей
> интеграции. Если доставка не настроена, оставьте оба секрета пустыми;
> периодическая сверка через API работает отдельно. См. [платежи](payments.md)
> и [lifecycle счетов](invoice-lifecycle.md).

Workers, интервалы, таймауты, размеры порций и границы выборок имеют внутренние
значения по умолчанию. Их переопределение необязательно. Не нужны флаги включения
каждой основной функции, пилотные списки клиентов, подтверждения
`EXCLUSIVE_WRITER` и ручные номера ревизий. Намеренно необслуживаемые аккаунты
можно указать в `REGISTRATION_EXCLUDED_TELEGRAM_IDS`.

## Логирование

`LOG_LEVEL` задаёт минимальный уровень JSON-логов: `debug`, `info`, `warn` или
`error`. По умолчанию (включая пустое значение) используется `info`. Регистр
не важен, пробелы по краям удаляются. Другие значения останавливают запуск;
ошибка называет допустимые уровни, но не выводит значение из окружения.

Обычный запуск пишет логи в stdout. CLI с JSON-отчётом сохраняют логи в stderr,
чтобы stdout содержал только отчёт. Настройка меняет только фильтрацию логов,
не формат отчётов и не поведение приложения.

Для Docker / Komodo добавьте `LOG_LEVEL=debug` в окружение сервиса (или его
приватный env-файл) и пересоздайте контейнер. После обновления образа нужен
pull + redeploy. Для последующей смены уровня пересборка образа не требуется,
но обычный restart не подхватит изменённое окружение Compose.

```sh
docker compose logs --since 30m --timestamps -f payplump
```

Ошибки сверки Ninja / S-UI записываются на `WARN` уже при стандартном `info`:
`service`, `operation`, `category`, `http_status`, `diagnostic_code`.
Код совпадает с Telegram-уведомлением. Этапы: `customers`, `recurring`, `invoices`
для Ninja и `inventory` для S-UI. Категории различают HTTP-ошибку, `timeout`,
`dns`, `tls_authority`/`tls_hostname`/`tls_certificate`, `connection_refused`,
`connection`, `invalid_response`, `incomplete_inventory`, `response_read`,
`response_too_large`, `canceled` и нераспознанное `unavailable`.
`http_status=0` (в Telegram — прочерк) означает, что статус не определён;
это не HTTP-код, присланный сервером.

На `DEBUG` дополнительно видны начало/окончание scan, длительность и количество
полученных записей, а для HTTP GET этих inventory-чтений — длительность, статус
и числовой номер страницы (0, если пагинации нет). Полные URL, параметры запросов,
заголовки, тела ответов, credentials и исходные тексты ошибок не выводятся.
Тайминги и счётчики не участвуют в дедупликации Telegram: повтор той же причины
не спамит, смена категории или HTTP-статуса создаёт новое уведомление.

## Выбор транспорта Telegram

`TELEGRAM_WEBHOOK_URL` пустой или отсутствует — long polling: приложение само
получает updates у Telegram. Туннель и публичный адрес для Telegram не нужны,
`TELEGRAM_WEBHOOK_SECRET` не используется. HTTP-сервер остаётся для health и
отдельных Ninja/lifecycle endpoints; это не режим `serve-health`.

Если URL задан, сервис использует webhook: требуется HTTPS и путь
`/telegram/webhook`, а также корректный `TELEGRAM_WEBHOOK_SECRET`. Некорректный
URL или секрет — ошибка запуска без автоматического переключения на polling.
Отдельный флаг транспорта не нужен; выбор делается при старте процесса.

В обоих случаях бот проверяет identity через `getMe` и передаёт updates одному
обработчику с прежними проверками отправителя и устойчивой дедупликацией в БД.
При переходе на polling снимается прежний webhook; при настройке обоих режимов
`drop_pending_updates=false`. Новые updates подтверждаются только после коммита.

Перед сменой режима остановите старый экземпляр. Один bot token — один процесс,
включая переход Mac → сервер; используйте ту же БД с журналами и барьерами.
Telegram 409 останавливает конкурирующий poller, но не является глобальной
блокировкой всех возможных webhook/polling экземпляров. Polling не изолирует
пилот: обычный сервис по-прежнему автоматически принимает подходящих клиентов
рабочих панелей и запускает их обслуживание.

## Запуск и миграция старого файла

Приложение читает окружение процесса, а не загружает `.env` самостоятельно.
Передавайте приватный файл через свой launcher, среду Komodo или Docker Compose.
Не публикуйте его содержимое и не выводите обычный `docker compose config`,
который может развернуть секреты в терминал.

Из старого файла обычного сервиса удалите флаги этапов разработки,
`ACTIVATION_ALLOWED_TELEGRAM_IDS`, `INVOICE_LIFECYCLE_ALLOWED_TELEGRAM_IDS`,
ручные `*_REVISION` и операторский блок `IMPORT_VERIFY_*`. Не меняйте без
проверки подключения, тариф, валюту, исключения и остальные бизнес-данные.
Оставшийся старый `false` не будет молча проигнорирован: сервис остановится
с названием ключа и сообщением о миграции. Ручные ревизии, пилотные списки и
непустые `IMPORT_VERIFY_*` тоже отклоняются в обычном запуске.

Обычный запуск не превращается в health-only из-за `TELEGRAM_ENABLED=false`:
этот старый ключ тоже вызывает ошибку миграции. Для CI и локальной проверки
readiness без внешних функций есть явная команда `payplump serve-health`.
Она принудительно выключает фоновые функции, но применяет миграции и startup
fences, поэтому её используют только со своей disposable БД, не с production.
`healthcheck` остаётся клиентом `/readyz`. Read-only CLI вызываются отдельно
и не запускают фоновые workers из-за новых defaults.

## Существующие клиенты и разрешения

Политика обычного запуска: [Ninja как источник истины](ninja-authority.md).
Активный клиент с активным recurring означает включённую подписку;
пауза recurring или неактивный клиент — выключенную. Даты, суммы, сроки оплаты,
известные autobill-настройки и исторические платежи не подгоняются под тариф бота.

Сверка при старте и каждые пять минут читает полные ограниченные выборки.
Отсутствующий S-UI создаётся сразу с нужным enabled; существующий не изменяется.
Сохранённые bindings имеют приоритет над распознаванием имён. Неоднозначность,
смена source scope и неизвестный исход записи требуют проверки, а не повторного
создания. `REGISTRATION_EXCLUDED_TELEGRAM_IDS` и запрет импорта самого бота
сохраняются. Администратор может быть обычным клиентом.

Уведомления содержат Telegram ID, reason и безопасный код диагностики.
Одинаковая проблема не рассылается заново после scan/restart; изменение и
повторное появление после устранения получают новое поколение. Общий сбой API
не создаёт отдельное сообщение каждому клиенту. Смотрите расшифровку в
[ninja-authority.md](ninja-authority.md).

Наблюдение не подменяет payment proof. Старые immutable origins и unknown
барьеры сохраняются; legacy runtime/effect permissions отзываются при запуске.
Их workers больше не меняют existing S-UI или расписание Ninja. Персональный
URL требует отдельной свежей проверки authority entitlement, владельца и S-UI.

Ручные `import-verify`/`import-apply` остаются историческими финансовыми
инструментами; [их ограничения](import-compatibility.md) не являются правилами
автоматического учёта клиентов. Не правьте hashes и unknown-барьеры вручную.

## Обычный запуск в Docker / Komodo

Используйте корневой `compose.yaml`: один контейнер с опубликованным образом,
внешняя PostgreSQL, обычный приватный env-файл. Пошагово:
[docs/deployment.md](deployment.md). `PAYPLUMP_ENV_FILE` по умолчанию `.env`;
можно задать абсолютный путь на Docker-хосте. Отдельный pgpass, manifest,
owner-approval и операторские CLI для обычного запуска не нужны.

## Расширенный release Compose (необязательный)

`compose.release.yaml` получает путь `PAYPLUMP_ENV_FILE` к приватному runtime
файлу вне репозитория. Нужен обычный файл без symlink, mode `0600`.
PostgreSQL-подключение задаётся отдельно; приватный `PGPASSFILE` монтируется
как secret. Контейнер принудительно получает пустые `DATABASE_URL`, `PGPASSWORD`
и остальные неиспользуемые настройки pgx: `PGOPTIONS`, `PGSERVICE*`, параметры
SSL/auth, `PGTZ` и прочие overrides. Runtime-файл не может через них изменить
схему, сервис подключения, правила TLS или аутентификации. Список фиксирован
по поддерживаемому pgx и проверяется валидатором; заполнять эти пустые ключи
оператору не нужно.

Валидатор использует `config --no-env-resolution` с `/dev/null` вместо dotenv
файла интерполяции. Он проверяет пути и метаданные, не открывая runtime-файл и
не печатая его содержимое. Одного наличия флага недостаточно: Compose v2.38.2
всё ещё разбирает env-файл при `--no-env-resolution`. Поэтому helper сначала
проверяет поведение на собственном некорректном синтетическом файле и отклоняет
такой renderer до обращения к runtime-конфигурации. CI использует проверенный
SHA-256 бинарник Compose v5.6.1 и только собственные синтетические приватные
файлы. Реальный offline-render проверен на Compose v5.6.1 без daemon:
JSON может опускать `required=true` как значение по умолчанию; явное `false`
по-прежнему запрещено. Проверка также проходит с намеренно некорректным содержимым
синтетического runtime-файла, которое не читается и не попадает в JSON.
Это не запуск контейнера или release workflow. См. [release.md](release.md).

Long polling добавлен отдельным продолжением после раздела 15 плана.
Мастер настройки и перенос обычных бизнес-параметров из окружения в БД
не реализованы.
