# Что проверяется при импорте существующей подписки

Импорт читает Ninja/S-UI и сохраняет проверенные привязки в БД бота. Он не
переименовывает клиентов, не меняет тариф, срок оплаты, реквизиты, настройки
автосписания и не выравнивает противоречащие друг другу состояния сервисов.

## Какие настройки сохраняются, а не подгоняются под новый шаблон

- `due_date_days` существующего recurring сохраняется **как есть**, включая
  числовые строки, `terms`, пустое значение и `on_receipt`. Значение не используется
  ботом для расчёта периода и не отправляется в запросах изменения расписания.
  `on_receipt` остаётся политикой только для новых подписок, создаваемых ботом.
- Нулевая скидка допускает оба значения `is_amount_discount`. Флаг не стирается.
- Налоговые названия, ID и inclusive/exclusive-флаг при нулевых ставках
  сохраняются в исходном профиле. Ненулевые ставки этим не разрешаются.
- Личная конфигурация, имя подписки и исходная цена сохраняются. Текущая цена
  каталога не подменяет подтверждённую цену legacy-подписки.
- Пустой S-UI `subURI` означает отсутствие override: используется явно заданный
  `SUI_SUBSCRIPTION_BASE_URL`, не адрес панели и не угаданная ссылка. Непустой
  override должен совпадать с настройкой. Сырые настройки панели в evidence
  остаются исходными; выбранный публичный адрес отдельно связан с политикой.

Все сохранённые поля участвуют в хешах и повторных проверках. Разрешить исходное
значение не означает разрешить его последующее незаметное изменение. Перед
записью и после неё billing terms, цена, credentials и остальные нетронутые поля
должны совпадать с замороженным профилем.

## Поддержанный сейчас финансовый профиль

- Один однозначный клиент Ninja и S-UI: для legacy `id_number` совпадает с `name`.
- Одна действующая месячная подписка с выбранным `product_key`, одной строкой,
  количеством 1, положительной исходной ценой и согласованными суммами.
- Одна родная валюта; нет конвертации, ненулевых скидок, налогов, доплат и partial.
- `auto_bill="off"`, `auto_bill_enabled=false`: этот путь рассчитан на ручную
  оплату, а не на автоматическое списание через платёжный шлюз.
- `remaining_cycles=-1`: бессрочное месячное расписание, не завершающаяся серия.
- S-UI без лимита трафика, expiry, отложенного старта и автоматического reset;
  выбраны ожидаемые inbounds, совпадают credentials и сохранённая привязка.
- Включённый S-UI допускает как активный recurring, так и recurring на паузе:
  пауза выставления счетов не отменяет подтверждённый оплаченный период.
  При paused recurring исходное расписание может быть прошлым или пустым;
  для выдачи конфигурации срок доступа определяется проверенным платежом.
  Состояния и расписание при импорте не меняются. Администратору один раз
  ставится в очередь информационное сообщение, не блокирующий import issue.
- При выключенном S-UI по-прежнему поддержан paused recurring с текущим долгом
  и отдельным оплаченным историческим периодом. Черновики, завершённые и
  неподтверждённые финансовые состояния не исправляются предположением бота.
- Счета и полная оплата подтверждаются по API, а не по webhook или одному статусу
  `paid`. Неоднозначные текущие счета, неподтверждённые распределения платежей
  и изменившиеся источники остаются для проверки.

Это список текущих поддержанных возможностей, а не утверждение, что другие
настройки Ninja неправильные. Расширение финансового профиля требует реализации
и проверки соответствующего поведения, а не удаления случайного `if`.

## Почему остальные поля не приравнены к безвредному сроку оплаты

Проверено по публичным исходникам Ninja 5.13.50:

- [`SendRecurring`](https://github.com/invoiceninja/invoiceninja/blob/v5.13.50/app/Jobs/RecurringInvoice/SendRecurring.php)
  при `auto_bill="always"` включает автосписание создаваемого счёта независимо от
  текущего `auto_bill_enabled` шаблона. Поэтому один false-флаг не доказывает, что
  другое значение `auto_bill` безопасно для ручного cash-профиля.
- [`RecurringInvoice`](https://github.com/invoiceninja/invoiceninja/blob/v5.13.50/app/Models/RecurringInvoice.php)
  уменьшает конечный `remaining_cycles` и переводит серию в completed при нуле.
  Это реальное завершение подписки, а не формат представления числа.
- Тот же model поддерживает разные `due_date_days`. Импортированный адаптер
  отправляет только action/status либо next date и сохранённый exchange rate;
  исходный срок оплаты он не пересоздаёт.

Номер релиза в этих ссылках — источник проверки реализации, не ограничение
запуска бота. Рабочие API в ходе этой проверки не вызывались.

## После импорта recurring на паузе

Пауза сохраняется при импорте и чтении конфигурации; одна уже оплаченная
baseline-фактура не запускает продление. При **новой** подтверждённой оплате
следующего периода работает обычное управляемое продление: бот может
перенести расписание и возобновить recurring по новым финансовым доказательствам
и действующим разрешениям. Это не автоматическое исправление во время импорта.
Если позже возникнет просроченный неоплаченный счёт, уже существующая пауза
подтверждается чтением без повторного `stop`; отключение доступа требует
обычных проверок текущего долга и авторизации.

## Как читать отказ

Уведомление содержит код диагностики — начало `candidate` в логе. Поля `stage`
и `check` называют конкретную проверку. Например, `legacy_auto_bill` — отличие
от поддержанного режима ручной оплаты. Старый `paused_recurring_sui_enabled`
больше не является отказом: при подтверждённом активном оплаченном периоде
это только уведомление администратору. Бот не должен сообщать о дублях, если
проверка установила другую причину.
