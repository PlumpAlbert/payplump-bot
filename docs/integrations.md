# Invoice Ninja и S-UI: проверка интеграций

Read-only адаптеры используются командой `payplump check-integrations`.
Команда не подключается к БД бота, не применяет миграции, не настраивает Telegram,
не импортирует клиентов, не создаёт счета и не меняет доступ, даже если включена
регистрация. Обычный сервис включает регистрацию и активацию без этапных флагов;
`check-integrations` остаётся отдельной командой только для чтения. Read-only
клиент S-UI не имеет методов записи. Запуск сервиса описан в
[deployment.md](deployment.md), бизнес-настройки — в [configuration.md](configuration.md).

## Проверенные контракты

Чтение проверено на Invoice Ninja **5.13.47** и S-UI **v1.6.4**. Версия Invoice
Ninja получена из `X-APP-VERSION`, версия S-UI подтверждена владельцем в интерфейсе
панели. На этапе 7a отдельный GET `/apiv2/status?r=sys` также вернул
`obj.sys.appVersion = "1.6.4"`; команда `check-integrations` пока не делает этот
запрос и не выдаёт `SUI_VERSION` за автоматическую проверку. Эти номера обозначают
исторические источники изученного API, не список разрешённых релизов. Текущие
адаптеры не требуют точного номера Ninja/S-UI и не вызывают status/ping только
для проверки версии. Проверяются фактические ответы и данные.

Адреса, токены, ID продукта, inbounds и персональные данные не хранятся в этом
документе. Они задаются через окружение из локального `.env`. Тестовые JSON-файлы
в `internal/invoiceninja/testdata` и `internal/sui/testdata` созданы заново по
проверенной структуре: все имена, ID, суммы и даты синтетические.

### Invoice Ninja

Заголовки: `X-API-TOKEN`, `X-Requested-With: XMLHttpRequest`, `Accept: application/json`.
К адресу сервиса добавляется `/api/v1`; префикс установки сохраняется.

| GET endpoint | Назначение |
| --- | --- |
| `/api/v1/clients` | Клиенты, поле Telegram ID, признаки архива / удаления |
| `/api/v1/products` | Товары |
| `/api/v1/products/{id}` | Выбранный товар и его цена |
| `/api/v1/invoices` | Счета, суммы, остатки и строковые статусы |
| `/api/v1/payments?include=invoices` | `date`, массив `paymentables` и включённые счета |
| `/api/v1/recurring_invoices` | Расписания, `frequency_id`, `next_send_date`, `last_sent_date` |

Списки имеют `data` и `meta.pagination`. Страницы запрашиваются явно через
`page` / `per_page`; ссылки из ответа не открываются. Клиенты читаются до конца
с проверкой стабильности общего количества и отсутствия повторных записей.
Достижение лимита страниц — ошибка, а не завершённая сверка. Счета, платежи и
recurring проверяются только на первой странице, не больше двух записей каждого
типа: это проверка чтения и структуры, не полный аудит истории платежей.

API ID сохраняются строками. Telegram ID разбирается как каноническое положительное
`int64`, без округления, знака, пробелов и ведущих нулей. Поддержаны `id_number`
и `custom_value1`–`custom_value4`; внутреннее `id` и отображаемое `number` не
используются вместо Telegram ID. Для текущей установки выбран `id_number`.
Человеческое имя клиента не является ключом сопоставления.

Деньги сохраняются как `json.Number`, без преобразования во `float64`.
`archived_at` — целочисленный timestamp, `is_deleted` — boolean, `status_id` и
`frequency_id` — строки. Адаптер не принимает нулевой остаток за доказательство
оплаты: эти проверки выполняет отдельный [GET-verifier](payments.md).
Read-only `Client` не имеет методов записи. Отдельный
`BillingClient` поддерживает ограниченную регистрацию по исходникам версии
5.13.47 и синтетическим контрактам; реальные POST пока не проверены.

### S-UI

Заголовок авторизации — `Token`. К адресу панели добавляется `/apiv2`; нестандартный
путь панели сохраняется. HTTP разрешён для явно настроенного защищённого канала,
например NetBird. Для HTTPS проверка сертификата всегда включена. На сервере
развёртывания доступ в ту же частную сеть нужно обеспечить и проверить отдельно.

| GET endpoint | Проверенная структура |
| --- | --- |
| `/apiv2/clients` | `obj.clients`: массив; `id`, `name`, `enable`, `desc`, `remark`, `inbounds`, `expiry`, `volume` |
| `/apiv2/inbounds` | `obj.inbounds`: массив; числовой `id`, строковые `type` и `tag` |
| `/apiv2/settings` | Плоский `obj`, **не** `obj.settings`; `subURI`, `subPath`, `subPort`, `subDomain` — строки |
| `/apiv2/clients?id=ID` | Отдельная проверка этапа 7a: массив полных записей с `config`, `links` и reset-полями |
| `/apiv2/status?r=sys` | Отдельная проверка этапа 7a: `obj.sys.appVersion` |

Проверяется `success`: значение `false` означает ошибку даже при HTTP 200.
Удалённый `msg` в ошибки и отчёт не попадает. `desc` — подпись в панели,
`remark` — отдельное поле; ни одно не используется вместо идентификатора.

`name` — существующий идентификатор ссылки подписки, а не источник Telegram ID.
Сверка сообщает только о точном совпадении `id_number` / выбранного поля с `name`.
Это кандидаты для последующего контролируемого импорта, не разрешение менять
записи. Переименования, нечёткое сравнение имён и автоматическое исправление ID
не выполняются. Аккаунты S-UI без соответствия остаются вне управления бота.
Пилотный исполнитель первой активации управляет только собственными новыми
записями; это не разрешение забирать прежние или несопоставленные аккаунты.

`SubscriptionURL` умеет собрать ссылку с сохранённым `name` и `format=json`, но
команда её не выводит и не открывает. Личные конфигурации, работу sing-box,
отключение доступа и `closeSessions` в рамках этой проверки не испытывали.
Частичные read-only DTO нельзя отправлять обратно в `save`: это потеряло бы
неизвестные поля протокола. Для отдельной write-capability используются полные
документы и проверки из [этапа 7a](activation-adapters.md), без включения доступа.

## Окружение и запуск

Скопируйте имена из `.env.example`, а реальные значения храните только в `.env`
или настройках секретов. Для команды нужны:

- `INVOICE_NINJA_BASE_URL` — адрес сервиса без `/api/v1`, query и credentials;
- `INVOICE_NINJA_API_TOKEN`, `INVOICE_NINJA_PRODUCT_ID`;
- `INVOICE_NINJA_TELEGRAM_ID_FIELD` — например `id_number`;
- `SUI_BASE_URL` — адрес панели с её путём, без `/apiv2`;
- `SUI_API_TOKEN`, `SUI_INBOUND_IDS` — уникальные положительные ID через запятую;
- `SUI_SUBSCRIPTION_BASE_URL` — публичный префикс подписки без персонального `name` и query.

`INVOICE_NINJA_VERSION` необязательна: если задана, версия из API должна совпасть.
`SUI_VERSION` — необязательная ручная отметка; отчёт всегда показывает
`version_verified: false`, поскольку эта команда пока не запрашивает status/sys.

| Ограничение | По умолчанию | Допустимо |
| --- | --- | --- |
| `INTEGRATION_HTTP_TIMEOUT` | `10s` | `1s`–`30s` на HTTP-запрос |
| `INTEGRATION_PAGE_SIZE` | `50` | `1`–`100` записей на страницу Invoice Ninja |
| `INTEGRATION_MAX_PAGES` | `20` | `1`–`100` страниц клиентов |

Ответ одного запроса ограничен 4 MiB, вся команда — двумя минутами.
Перенаправления HTTP запрещены, чтобы не передать токен другому адресу.
Диагностика не содержит URL, токенов, тела ответа или персональных полей.

Из доверенного shell-совместимого `.env`:

```sh
set -a
. ./.env
set +a
CGO_ENABLED=0 go build -trimpath -o bin/payplump ./cmd/payplump
./bin/payplump check-integrations
```

Или в уже запущенном контейнере с доступом к API:

```sh
docker compose -f compose.dev.yaml exec -T app /payplump check-integrations
```

Команда выводит один JSON-отчёт в stdout; ошибки идут в stderr, код завершения
при ошибке ненулевой. Ошибка конфигурации обнаруживается до запросов API.
Отчёт содержит только количества, boolean-результаты и версии, без имён,
идентификаторов, цен, контактов и ссылок подписок.

`status: ok` подтверждает доступность чтения и проверенную структуру ответов,
но не готовность к автоматическому выставлению счетов или отключениям. Отсутствие точного
совпадения S-UI не означает отсутствие конфига: возможны старый идентификатор
или новый клиент без первой оплаты. Эти случаи, а также выключенные аккаунты
и отличия назначенных inbounds, отражаются счётчиками без изменения данных.
Дубли и некорректные непустые Telegram ID требуют ручной проверки и завершают
команду с ошибкой. Архивные / удалённые клиенты Invoice Ninja не участвуют в
сопоставлении, а клиенты без Telegram ID не становятся управляемыми автоматически.

## Следующие проверки

До включения операций записи нужно отдельно подтвердить на выделенных тестовых
записях создание и поиск клиента, выставление одного счёта, статусы оплаты,
due date, вебхуки и их авторизацию, stop/start recurring и даты 29–31.
Для S-UI — сохранение всех полей при редактировании, реальную JSON-подписку,
закрытие сессий, запрет повторного подключения и сохранение реквизитов после
восстановления. Импорт существующих клиентов сначала выполняется без изменений.
