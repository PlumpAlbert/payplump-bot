# Регистрация и первый счёт

В обычном режиме регистрация работает без `REGISTRATION_ENABLED`. Заполните
общие бизнес-параметры и интеграции по [инструкции обычного запуска](configuration.md):
в частности `TZ`, `PAYMENTS_CURRENCY_ID` и `PAYMENTS_CURRENCY_CODE`, продукт,
налоговый режим, `PAYMENT_PHONE` и настройки Telegram/Ninja. Основные функции
не выключаются отдельными флагами; частные actor/provenance-проверки, разрешения
и unknown-result барьеры остаются обязательными. Старые stage/pilot команды ниже
сохранены как исторические, а не как инструкция обычного запуска.

Команда `check-integrations` всегда выполняет только чтение.

Реализация проверена синтетическим HTTP, тестами восстановления и PostgreSQL
в отдельных схемах Neon. **Создание записей на установленном Invoice Ninja не
испытывали.** Для реального испытания нужно отдельное разрешение владельца и
заранее согласованный тестовый клиент. Рабочие записи для этого не подходят.

## Проверки перед реальным внешним тестом (не обычные startup-инструкции)

1. Подготовьте отдельного тестового Telegram-бота и проверьте реальный webhook.
   Одна БД обслуживает одного бота и одну компанию Invoice Ninja; тестовое
   окружение не должно использовать БД рабочего бота.
2. Выполните `check-integrations`. Токен должен видеть полную историю клиентов
   и счетов компании, не только назначенные его пользователю записи. Чтение
   должно работать; это ещё не проверка записи.
3. Проверьте продукт, валюту по умолчанию, налоги, реквизиты и таймзону процесса
   (`TZ`; в Compose по умолчанию `UTC`). Даты берутся из локального календаря
   процесса, а не из времени доставки Telegram или настроек панели.
4. Подтвердите приватно Telegram ID пользователей, намеренно оставленных вне
   биллинга, и заполните `REGISTRATION_EXCLUDED_TELEGRAM_IDS`. Не выводите ID
   из отображаемого имени. Исключённый пользователь не вызывает даже GET
   Invoice Ninja; задание останавливается с кодом `1008`, доступ не меняется.
   Не сопоставленные записи S-UI автоматически не импортируются.
5. Перед разрешённым живым тестом проверьте очередь: будут обработаны и ранее
   накопленные задания. Подходящие существующие клиенты проходят отдельную строгую
   auto-import в БД; клиент без подтверждённой собственной связи не получает новый
   первый счёт автоматически.
6. Проверьте уведомления и автоматизации Invoice Ninja. `mark_sent` не вызывает
   endpoint отправки email, но события, напоминания и административная почта
   зависят от настроек установки. Параллельные внешние записи в создаваемые
   ботом документы не поддерживаются.
7. Реальные записи требуют отдельного разрешения и выделенной тестовой записи;
   не трактуйте обычный startup как разрешение на живой тест.

Требуется Invoice Ninja **5.13.47**. Исходники операций изучены на коммите
[`493c3884e4214028bc5970cb41bafbd9c4d96401`](https://github.com/invoiceninja/invoiceninja/tree/493c3884e4214028bc5970cb41bafbd9c4d96401).
Это проверка исходного кода и синтетических контрактов, не свидетельство
реального успешного POST на установленном сервисе. Перед каждым POST выполняется
аутентифицированный GET и проверяется `X-APP-VERSION`; ответ POST проверяется тоже.

## Настройки

Помимо включённого и настроенного Telegram нужны:

| Переменная | Значение |
| --- | --- |
| `INVOICE_NINJA_BASE_URL`, `INVOICE_NINJA_API_TOKEN` | Адрес установки без `/api/v1` и токен |
| `INVOICE_NINJA_PRODUCT_ID` | API ID активного товара |
| `PAYMENTS_CURRENCY_ID`, `PAYMENTS_CURRENCY_CODE` | Родная валюта компании: внутренний ID и подтверждённый ISO-код |
| `INVOICE_NINJA_TELEGRAM_ID_FIELD` | Для записи только `id_number` |
| `INVOICE_NINJA_INCLUSIVE_TAXES` | Обязательное `true` или `false` по принятой схеме ценообразования; пустое значение запрещено |
| `PAYMENT_PHONE` | Телефон для перевода в сообщении клиенту |
| `PAYMENT_BANK`, `PAYMENT_RECIPIENT` | Необязательные подписи реквизитов |
| `REGISTRATION_EXCLUDED_TELEGRAM_IDS` | Необязательный список уникальных положительных Telegram ID через запятую, максимум 1000 |
| `REGISTRATION_WORKERS` | По умолчанию `1`, допустимо `1`–`4` |
| `REGISTRATION_POLL_INTERVAL` | По умолчанию `1s`, допустимо `100ms`–`1m` |
| `REGISTRATION_HTTP_TIMEOUT` | По умолчанию `5s`, допустимо `1s`–`10s` |
| `INTEGRATION_PAGE_SIZE`, `INTEGRATION_MAX_PAGES` | По умолчанию `50` и `20`, каждый параметр `1`–`100` |

Для Telegram задайте 1–99 уникальных положительных ID администраторов.
Необязательный `INVOICE_NINJA_VERSION` может указывать только `5.13.47`;
он не заменяет проверку версии через API. Секреты, реальные ID и реквизиты
хранятся в окружении, не в Git. Приложение само не загружает `.env`.

## Последовательность

Каждый захват выполняет не больше одного внешнего изменения:

1. Найти клиента по точному `id_number`, включая архивные и удалённые записи.
   При отсутствии создать клиента с приватным маркером владения заданием.
2. Проверить историю его счетов, прочитать текущий товар и создать обычный
   черновик с одной строкой. Копируются `product_key`, описание, **цена** товара
   и три набора налогов; цена не заменяется себестоимостью. Строка имеет тип
   товара и нулевую скидку. Дополнительные скидки, налоги на весь счёт, сборы,
   депозиты и уже зачтённые платежи не поддерживаются и останавливают обработку.
   Дата и due date совпадают. Запрос не содержит recurring, оплаты, auto-bill
   или email-флагов.
3. Убедиться в принадлежности и неизменности финансовых полей черновика,
   нулевом балансе черновика и текущей дате; выполнить `mark_sent` для одного ID.
   В этой версии Invoice Ninja выставление добавляет сумму к балансу и ledger;
   статус `sent` сам по себе не подтверждает завершение всех изменений.
4. Заново прочитать выставленный счёт и атомарно сохранить соответствия клиента,
   первого / текущего счёта, завершение задания и сообщения outbox.

Номер, итоговая сумма и HTTPS invitation link берутся из конкретного счёта.
Сумма не пересчитывается локально и не округляется через `float64`. Внешние
имена и описания могут меняться или раскрывать шаблонные переменные; они не
заменяют Telegram ID, приватный маркер и проверку финансовых полей.

Состояние остаётся `awaiting_payment`, доступ выключен, recurring и S-UI ID
пусты. [Наблюдение ручной оплаты](payments.md) работает в обычном режиме и само
не выдаёт доступ. Этот поток регистрации сам не активирует клиента и не проверяет
просрочку; последующие этапы первой активации и lifecycle-обработка
описаны в [activation.md](activation.md) и [invoice-lifecycle.md](invoice-lifecycle.md).
[Клиентское меню](client-menu.md) работает отдельно от регистрации; кнопка
конфигурации проверяет собственное managed provenance и текущее право на выдачу.

## Сбои и ограничения восстановления

Миграция `005_registration_work.sql` добавляет `first_invoice_id`, уникальное
задание регистрации на клиента, `registration_flows` и `operation_steps`.
Прежние миграции не изменяются. До POST фиксируется неизменяемый запрос;
разрешение на POST выдаётся только при первой подтверждённой вставке намерения.
HTTP-транспорт не повторяет POST и не следует redirect.

Если подтверждение коммита БД потерялось, запрос не отправляется. Если ответ
создания потерялся, через 30 секунд выполняется только поиск: точное совпадение
Telegram ID / клиента, приватного маркера и сохранённого запроса может подтвердить
результат. Отсутствие записи, дубли или несовпадение требуют ручного разбора,
а не ещё одного POST. Это защита от повторов бота, **не серверная гарантия
exactly-once**: поддерживаемого ключа идемпотентности у этих endpoint нет.

Неизвестный исход `mark_sent` всегда останавливает задание, даже если следующий
GET показывает `sent` и правильный баланс. Повторять выставление или считать
ledger завершённым по одному статусу нельзя. При переходе календарной даты
между созданием и выставлением также требуется проверка: бот не меняет старый
запрос и не создаёт замену счёта.

Аренда — 2 минуты, попытка — до 1 минуты, запрос БД — до 8 секунд.
Истёкшая аренда запрещает старому исполнителю менять локальный результат.
При остановке HTTP отменяется, известный результат и перенос задания используют
один срок до 8 секунд; оба фоновых обработчика завершаются до закрытия БД
в пределах общего 10-секундного shutdown. Прерывание процесса всё равно может
оставить неопределённый внешний результат и потребовать ручного разбора.

### Остановленные задания

Задание остаётся `pending`, `locked_until = NULL`, `next_attempt_at = 'infinity'`.
Оно блокирует более новые операции своего клиента. Администраторы получают
локальный ID задания и код причины, без тела API или секрета маркера:

| Код | Причина |
| --- | --- |
| `1001` | Существующий клиент без подтверждённого владения; нужен импорт |
| `1002` | Конфликт клиента |
| `1003` | Конфликт счёта / истории |
| `1004` | Неизвестный исход записи |
| `1005` | Неподходящее состояние или дата счёта |
| `1006` | Несовместимый контракт / настройки |
| `1007` | Изменённое локальное состояние или соответствия |
| `1008` | Явное исключение пользователя из автоматического биллинга |

После устранения причины оператор с доступом к БД может вернуть задание в очередь:

```sh
./bin/payplump resume-registration OPERATION_ID
```

Это команда управления **только локальным заданием**: без миграций, Telegram
или внешних API. Она не удаляет намерения, не меняет подтверждения и не выдаёт
новое разрешение на POST. Например, поздно появившийся созданный объект может
быть найден после возобновления, но неизвестный `mark_sent` снова остановится.
Команда не является инструментом подтверждения ledger или импорта. Для таких
случаев нужен отдельный проверенный процесс ручного восстановления; пока его
нет. Не удаляйте строки журнала ради повторной отправки и не подменяйте маркеры.

Перед обновлением остановите старые экземпляры и сохраните резервную копию БД.
Старый бинарник не понимает миграцию `005`; откат одного бинарника без проверки
совместимости схемы не поддерживается.
