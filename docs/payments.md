# Проверка оплаты Invoice Ninja

В обычном режиме проверка оплаты работает без `PAYMENTS_ENABLED`; отдельные
флаги основных функций не требуются. Заполните бизнес-параметры и интеграции по
[инструкции обычного запуска](configuration.md), включая родные
`PAYMENTS_CURRENCY_ID` и `PAYMENTS_CURRENCY_CODE`. Actor/provenance-проверки,
разрешения и unknown-result барьеры при этом обязательны. Старые stage/pilot
команды ниже не являются инструкцией обычного запуска. Настройка исходящих
webhook в Invoice Ninja автоматически не выполняется.

Этап фиксирует наблюдение об оплате и расчётные даты. **Он не выдаёт доступ,
не меняет S-UI, не создаёт / возобновляет recurring и не ставит задания активации.**
Эти действия выполняет [поток активации](activation.md), который заново
проверяет актуальные платёжные данные перед каждым внешним изменением. Сама
проверка платежей не меняет состояние доступа или `desired_access`.

Реализация проверена синтетическим HTTP и отдельными схемами Neon. Настоящие
платежи, webhook установленного сервиса и банковское поступление не испытывали.
Настройки рабочих интеграций не менялись; для внешнего теста нужно разрешение
владельца и выделенный тестовый клиент.

## Настройки

Нужны настроенный Telegram, проверенный bot ID и 1–99 уникальных положительных ID администраторов.

| Переменная | Значение |
| --- | --- |
| `PAYMENTS_CURRENCY_CODE` | Подтверждённый оператором трёхбуквенный ISO-код родной валюты |
| `INVOICE_NINJA_BASE_URL`, `INVOICE_NINJA_API_TOKEN` | База API без `/api/v1`, токен с полным чтением платежей компании |
| `INVOICE_NINJA_TELEGRAM_ID_FIELD` | Только `id_number` |
| `INVOICE_NINJA_WEBHOOK_SECRET` | Отдельные 32–256 символов `A-Z a-z 0-9 _ -`, не API / Telegram секрет |
| `PAYMENTS_CURRENCY_ID` | Обязательный заранее проверенный API ID собственной валюты компании, не `RUB` / `USD` и не код ISO |
| `PAYMENTS_WORKERS` | По умолчанию `1`, допустимо `1`–`4` |
| `PAYMENTS_POLL_INTERVAL` | По умолчанию `1s`, допустимо `100ms`–`1m` |
| `PAYMENTS_RECHECK_INTERVAL` | По умолчанию `5m`, допустимо `30s`–`1h` |
| `PAYMENTS_HTTP_TIMEOUT` | По умолчанию `5s`, допустимо `1s`–`10s` на GET |
| `INTEGRATION_PAGE_SIZE`, `INTEGRATION_MAX_PAGES` | По умолчанию `50` / `20`, каждый `1`–`100` |
| `REGISTRATION_EXCLUDED_TELEGRAM_IDS` | Явно исключённые пользователи не вызывают API и не получают подтверждение |

Поддерживается только **Invoice Ninja 5.13.47**; версия проверяется в ответе
каждого GET. Декларация `INVOICE_NINJA_VERSION`, если задана, должна совпасть.
Валюта по умолчанию берётся из явно подтверждённой оператором политики компании.
Явное переопределение валюты клиента должно совпадать; неизвестные групповые
настройки, FX и другая валюта требуют проверки. Автоматического определения
валюты компании или конвертации здесь нет.

Одна БД обслуживает одного бота и одну компанию. В проверку попадают только
клиенты с подтверждённым managed provenance этого бота и совпадающими customer /
invoice ID и сохранённым текущим счётом. Подходящие legacy-кандидаты проходят
отдельный строгий auto-import; сам verifier не принимает произвольные внешние
клиенты или несопоставленные записи S-UI.

## Входящий webhook

Путь: `POST /invoiceninja/webhook`, `Content-Type: application/json`.
Завершите HTTPS на доверенном reverse proxy и передавайте заголовок
`X-Payplump-Webhook-Secret` с отдельным секретом. Сравнение постоянного времени
выполняется до чтения тела и обращения к БД. Это общий секрет в пользовательском
заголовке, **не HMAC, подпись или встроенный стандарт Invoice Ninja**.

До завершения проверки Telegram bot ID endpoint возвращает 503. При включённом
обработчике принимается один JSON-объект до 1 MiB. После коммита метаданных —
HTTP 200; при ошибке БД — 503, неверном секрете — 403, неверном JSON — 400,
типе содержимого — 415, превышении размера — 413. Несколько значений секретного
заголовка отклоняются.

Внешние `id`, статусы, суммы и даты **не разбираются как доказательство или
селектор счёта**. Сохраняются SHA-256 исходного тела и bot ID, без самого тела,
контактов или секрета. Новый хеш атомарно увеличивает поколение запроса сверки.
Повтор одинакового тела не создаёт новую бизнес-обработку. Разный JSON одного
события может дать ещё один безопасный сигнал; полноценной идентичности событий
исходящие webhook этой версии не предоставляют.

### Настройка отправителя выполняется владельцем

Контракт изучен по [исходникам 5.13.47](https://github.com/invoiceninja/invoiceninja/tree/493c3884e4214028bc5970cb41bafbd9c4d96401),
а не реальной доставкой. Исходящие подписки: invoice-created `2`, invoice-updated
`8`, payment-created `4`, payment-updated `31`. Отдельной подписки invoice-paid
нет: `InvoiceWasPaid` — внутреннее событие. Тело — преобразованная сущность,
не конверт `{event,data}`; встроенного UUID доставки / HMAC нет. Для нашего
приёмника задайте POST и пользовательский секретный заголовок.

Особенность отправителя важна при внедрении: эта версия не повторяет 5xx,
а ответы 404 / 405 / 410 могут удалить подписку webhook. Поэтому сначала
включите и проверьте приёмник; не отключайте его, оставив рабочую подписку.
Пропущенные сигналы обязательно покрывает периодическая сверка. Приложение
не вызывает API создания / изменения этих подписок.

## Доказательство оплаты

Источник — точные сохранённые ID, не поиск по имени. Проверяются владелец счёта,
`client_id`, точное `id_number` Telegram, состояние счёта, валюта и суммы.
Текущий первый счёт должен оставаться обычным; для будущего recurring требуется
точная сохранённая связь расписания.

GET платежей использует `client_id`, `include=invoices`,
`status=active,archived,deleted`, `sort=id|asc`. **Фильтр `invoice_id` не
поддерживается** этой версией и мог бы быть молча проигнорирован. Все страницы
читаются до конца с проверкой счётчиков и уникальности ID. Дополнительные
пределы — 2000 платежей и 4000 allocation на один проход; в положительном
доказательстве не больше 1000 allocation и 64 KiB с учётом форматирования JSONB.
Усечение / ошибка
не являются подтверждением оплаты; внешние ссылки пагинации не открываются.

Положительный результат требует одновременно:

- не архивный / удалённый счёт со статусом `4`, положительной суммой,
  нулевым остатком и `paid_to_date`, равным полной сумме;
- завершённые (`status_id=4`) **ручные** платежи, не удалённые / архивные,
  без возврата и конвертации, в подтверждённой собственной валюте;
- живые положительные `paymentables` именно этого счёта, с верным `payment_id`,
  уникальными allocation ID и непротиворечивыми суммами;
- `applied`, равный сумме invoice-allocation платежа и не превышающий `amount`;
- сумма подходящих cash-allocation **точно равна** сумме счёта.

Pending / failed / cancelled / refunded, не ручные и архивные платежи не
служат доказательством. Частично возвращённые источники пока не поддерживаются.
Платёж с allocation кредита целиком исключается: invoice-allocation смешанного
cash / credit может превышать фактическую денежную часть. Другие чистые ручные
платежи могут независимо подтвердить всю сумму. `paid_to_date`, статус `paid`,
неверный счёт и нулевой остаток после отмены не заменяют этих проверок.

Это проверка учётных записей, внесённых владельцем, не банковской выписки или
фактического процессингового settlement. `is_manual` не является подписью человека.

Для положительного результата целиком повторно читаются платежи, счёт и клиент.
Сравниваются все прочитанные факты с нормализацией порядка и десятичных чисел,
а не только использованные allocation. Изменение во время чтения переносит
проверку. API всё равно не даёт транзакционного снимка нескольких GET;
последующий исполнитель доступа обязан заново проверить актуальность.

## Даты и повторная обработка

При нескольких частичных оплатах берётся дата достижения полной суммы из
`Payment.date`; при точном покрытии положительными allocation это последняя
из их бизнес-дат. Будущая / некорректная дата отклоняется. Прибавляется один
календарный месяц с ограничением последним днём: 31 января → 28/29 февраля.
Правило ещё нужно проверить на установленном recurring до его включения.

Дата прихода webhook не подменяет дату платежа: перевод 20 октября, внесённый
21 октября, даёт расчётную дату 20 ноября. Отметка 18-го за перевод 17-го —
17 ноября. Дата в Invoice Ninja редактируется владельцем; она не является
неизменяемым банковским timestamp.

Миграция `007_payment_verification.sql` добавляет bot-scoped wake / dedup,
независимую очередь проверок и `payment_confirmations`. На один опрос добавляется
не больше 50 новых подходящих клиентов. Конкурирующие исполнители используют
аренду 2 минуты и монотонную попытку, попытка ограничена минутой, запросы БД —
8 секундами. Старый исполнитель не может завершить или перенести чужую аренду.
Новое поколение webhook после захвата не теряется при завершении старой попытки.
После временной ошибки оно не обходит retry-cooldown, а остаётся ожидающим до срока.

Первое подтверждение, `payment_date` / `next_invoice_date` подписки и уведомления
outbox фиксируются атомарно. Повтор того же доказательства не меняет даты и не
создаёт второй период. Новый источник / дата / сумма для уже подтверждённого
счёта либо его последующее неподтверждённое состояние требуют ручной проверки:
оригинальные данные сохраняются, `review_required` остаётся установленным.
Даже возврат исходного доказательства сам эту отметку не снимает.

Ошибка сети / API, несовместимая версия или неполное чтение переносят запрос
без объявления неоплаты и без sticky-review старого подтверждения. Временные ошибки
повторяются с задержкой до пяти минут; при 429 задержка не меньше минуты.
Проверки не используют FIFO внешних операций, поэтому остановленная регистрация
не скрывает наблюдение уже управляемого счёта. Интерактивное меню также не блокируется.

Статус меню показывает сохранённую проверенную дату и необходимость перепроверки;
он не подтверждает текущее соединение S-UI. Новое уведомление отделяет факт
платежа от состояния доступа; активация учитывается другим исполнителем.
Расчётная будущая дата не означает, что расписание уже создано. Исторические несохранённые счета не продлевают период;
общий аудит прошлых периодов / refund после смены текущего счёта пока не реализован.

Поддерживаемого инструмента для изменения / снятия sticky-review в этом этапе
нет. Нужен отдельный проверенный процесс восстановления, а не удаление доказательств
ради повторного продления. `payments.Observe` переиспользует полный GET-протокол
без записи; активация требует совпадения с оригиналом и неистёкшего периода.
