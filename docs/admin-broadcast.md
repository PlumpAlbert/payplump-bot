# Административная рассылка

Команды рассылки доступны в обычном режиме, но startup никогда не отправляет
сообщение автоматически: каждая фактическая рассылка требует admin preview,
замороженной аудитории и отдельного confirmation. Она не выдаёт персональные
конфигурации и не меняет оплату или VPN-доступ. Заполните Telegram и admin ID по
[инструкции обычного запуска](configuration.md). Ревизии политики внутренние,
монотонные в БД; restart не восстанавливает отключённую политику. Разработка и
тесты не отправляют сообщения реальным пользователям.

## Включение владельцем

Для административных команд нужны настроенный Telegram и точные приватные
`TELEGRAM_ADMIN_IDS`. Ревизия рассылки хранится внутренне в БД; вручную её
задавать не нужно. Параметры исполнения:

- `BROADCAST_MAX_RECIPIENTS`: по умолчанию 1000, допустимо 1–10000;
- `BROADCAST_BATCH_SIZE`: по умолчанию 50, допустимо 1–50;
- `BROADCAST_WORKERS`: по умолчанию 1, допустимо 1–8;
- `BROADCAST_POLL_INTERVAL`: по умолчанию 1s, допустимо 100ms–1m.

Хэш фиксирует версию контракта, канонические admin IDs и предел аудитории.
Ревизия — отдельный монотонный DB fence. Изменённая политика с прежней/старой
ревизией отвергается; restart не переактивирует отозванную политику.

## Команды в приватном чате

1. `/broadcast` — инструкция административного меню.
2. `/broadcast_text <текст>` — новый приватный черновик и предпросмотр текста.
3. `/broadcast_all <токен A>` — сервер замораживает получателей и показывает число.
   Возвращается **новый токен B**; старый уже не разрешает подтверждение.
4. `/broadcast_confirm <токен B>` — явное создание одной долговечной рассылки.
5. `/broadcast_status <токен B>` — агрегированные pending/queued/sent/failed/skipped.
6. `/broadcast_cancel <токен>` — отмена ещё не подтверждённого черновика.

Текст ограничен 3000 UTF-8 байт, без разметки; переводы строк и табуляция
разрешены. Зарезервированный protected-intent marker не принимается как текст.
Новый текст отменяет прежний неподтверждённый черновик, а не редактирует
подтверждённую рассылку. Токены имеют 192 бита случайности, действуют для
подтверждения 15 минут и привязаны к bot/actor/private chat. Часы БД проверяются
после ожиданий блокировок. Группы, чужие отправители и адресация другому боту
не принимаются. При каждом действии проверяется **текущая политика БД**, а не
только прежний список администраторов процесса.

Текст, токены и preview находятся в приватном outbox/БД. Они не попадают в
обычные журналы. Не публикуйте дампы, содержимое outbox или скриншоты токенов.

## Аудитория и доставка

Получатели — известные локальные клиенты с доказанным приватным взаимодействием
именно с этим ботом. Начальная membership может восстанавливаться только из
собственного completed registration journal или matching private menu outbox.
Одна глобальная строка клиента, чужой bot journal, username или имя человека
такого права не дают. Участники вне billing могут получать обычные объявления:
это не принимает их под управление подписками.

Текст и audience snapshot неизменны. Новый участник **после предпросмотра
аудитории**, даже до подтверждения, не включается. При превышении cap частичный
snapshot откатывается. Перед enqueue заново проверяется сохранённая связка
client/actor/chat/membership под блокировками; изменённая связка пропускается.

Worker создаёт до 50 recipient outbox rows за batch. HTTP делает существующий
обычный outbox worker: приватный FIFO, общий Telegram 429 cooldown и известные
per-recipient ошибки. Один заблокировавший бота получатель не блокирует других.
Завершение означает, что **все** delivery rows пропущены или их outbox terminal
(sent/failed), а не просто поставлены в очередь. Администратору создаётся один
итог с агрегированными числами. Повтор update/confirm/restart не создаёт новый job.

Доставка обычная **at-least-once**: при неизвестном результате Telegram запрос
может повториться и сообщение может продублироваться. Это не exactly-once и
не protected-secret протокол. Подтверждённый job нельзя отозвать командой отмены.
Выключение/новая политика прекращают новый fanout старого job, но не обещают
отозвать уже разрешённые queued/in-flight обычные сообщения. Для секретов
используется отдельный защищённый `/config`, не рассылка.

## Проверки

Unit/race покрывает parser, canonical policy, приватную сериализацию, worker
cancellation/join и routing. Изолированные PostgreSQL тесты проверяют политику,
cap rollback, immutable snapshot/deliveries, batch 50+1, terminal summary и
реальное private-menu membership без adoption чужого бота. Синтетический HTTP
workflow использует настоящий Telegram webhook handler → broadcast gateway →
store → batch/outbox workers → loopback Telegram transport; проверяет rotated
confirmation, eligible late member exclusion, blocked recipient, dedup и restart.
Deadline-sensitive позитивный workflow обязателен в CI на loopback PostgreSQL;
остальные проверки БД остаются на Neon. Production-доставки этим не разрешены.
