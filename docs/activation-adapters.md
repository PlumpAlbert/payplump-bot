# Адаптеры подготовки доступа: этап 7a

Это контрактный слой, **не автоматическая активация**. Новые write-клиенты не
создаются при старте приложения, не вызываются из webhook, меню или проверки
платежей. Новых флагов включения доступа, миграций состояния активации и выдачи
персональных ссылок в этом этапе нет. `PAYMENTS_ENABLED` по-прежнему только
сохраняет наблюдение об оплате.

Все операции записи проверяются на синтетическом HTTP. Настоящие клиенты,
recurring, доступ S-UI и сообщения Telegram не создавались / не менялись.
Нужны отдельные разрешение владельца и тестовая запись, прежде чем испытывать
запись или включать будущий исполнитель.

права токенов, сетевую доступность, автоматизации и работу ядра проверяет владелец.

## Общие правила будущего вызова

До каждого POST вызывающий слой обязан:

1. Заново проверить принадлежность текущего счёта, полную оплату и неизменность
   подтверждения; `review_required` должен отсутствовать.
2. Проверить, что рассчитанный период и первый запуск recurring не истекли.
3. Захватить fenced-операцию клиента и зафиксировать неизменяемое намерение,
   включая случайное имя / реквизиты S-UI и запрос расписания.
4. Вызвать один внешний шаг; сохранить известный результат отдельно от следующих.

Ни у одного из этих endpoint нет пригодного серверного ключа идемпотентности.
HTTP-транспорт не повторяет POST и не следует redirect. Любая ошибка после
передачи запроса может означать неизвестный результат. Повторное обнаружение
объекта и разрешение следующего изменения — разные решения. Старое намерение
не удаляют ради повторной отправки.

Адаптеры не реализуют этот журнал вместо исполнителя. Наличие метода записи
не является проверкой оплаты или разрешением управлять произвольным аккаунтом.
Ошибки `sui.ErrManagedUnknown` и `invoiceninja.ErrRecurringUnknown` требуют
сохранения намерения и разбора результата, а не автоматического повторного POST.
Параллельные ручные / посторонние изменения не поддерживаются: API не даёт CAS.
Предварительная проверка снимка сокращает риск, но не делает GET+POST атомарными.

## S-UI

Авторизация: `Token`, префикс установленной панели сохраняется. HTTP разрешён
для явно настроенного защищённого канала NetBird; HTTPS проверяет сертификат
и имя сервера. Отключения TLS-проверки нет.

Обычный `GET /apiv2/clients` возвращает **неполные сводки**. Перед изменением
нужен `GET /apiv2/clients?id=ID`: `obj.clients` остаётся массивом. Поддержаны
группы ID через запятую; отсутствие записи — не разрешение пересоздать её.
Read-only `Account` не предназначен для обратной отправки в `save`.

Запись использует form-urlencoded:

```text
POST /apiv2/save
object=clients
action=new | edit
data=<полный JSON клиента>
```

Это не JSON-конверт и не PATCH. Низкоуровневый `Writer.PostForm` также выключает
повтор тела и redirect, кодирует снимок данных и ограничивает размер.
`success:false` при HTTP 200 означает ошибку; удалённый `msg` не раскрывается.

Для нового клиента нужны три разные сущности: серверный числовой ID, случайное
имя подписки и протокольные credentials. Backend не генерирует недостающие
секреты. `NewDisabledDraft` готовит отключённую запись с CSPRNG-материалом, корректными
протокольными полями и нулевыми лимитами / reset-полями. Имя и секреты должны
попасть в защищённый журнал **до POST**, а не генерироваться заново при повторе.

Имя глобально проверяется приложением, но уникального индекса БД нет; UUID
глобально не проверяется. Поэтому создание требует полного ограниченного
инвентаря и проверки столкновений имени / credentials. UUID сравниваются по
разобранной идентичности, включая compact / braced / URN-формы. Коллизии повторно
проверяются перед enable и при чтении результата. Нельзя искать клиента по
отображаемой подписи или автоматически забирать несопоставленную запись.

Изменение существующей записи требует доверенной сохранённой привязки числового
ID, точного имени и fingerprint конфигурации. Действие меняет только разрешённое
поле, не пересоздаёт имя / UUID / пароль / inbounds. Неизвестные поля конфигурации
сохраняются; неизвестные верхнеуровневые поля требуют отказа, поскольку backend
модели мог бы их отбросить. Небезопасные числа в конфигурации отклоняются: backend
нормализует её через `float64`, что может округлить большие целые.

`NewManagedClient` требует явно подтверждённую версию и предел 1–1000 клиентов.
`GetRecord` читает полную запись; `CreateDisabled` создаёт только отключённую,
а `FindCreated` выполняет отдельную положительную сверку. `PrepareEnable`
замораживает снимок / привязку; `Enable` допускает только false → true, не
принимая уже включённую запись за подтверждение прошлого шага. JSON этих типов
содержит секреты и предназначен для защищённого журнала, не логов.

Backend управляет timestamps / traffic counters и перегенерирует локальные
links. Внешние / nonlocal links сохраняются. Особенность исходников: передача
`up=down=0` означает сброс трафика. Поэтому enable с ненулевым объёмным лимитом
и нулевыми счётчиками отклоняется и при подготовке, и после свежего GET:
фоновый stats tick мог бы иначе добавить расход между чтением и сбросом.
При безлимитном объёме нулевые счётчики допустимы; точная неизменность внутренних
счётчиков не обещается. Delay-start и periodic-reset политики также отклоняются.

После успешного ответа обязателен новый GET полной записи. Ответ `save` содержит
общий список, а ошибки commit в этой версии могут только логироваться; одного
HTTP / `success:true` недостаточно. Даже чтение из БД не доказывает согласованность
ядра sing-box или работоспособность подключения.

Отключение и `closeSessions` относятся к будущему этапу просрочки. Один kick не
выключает клиента, а periodic/global resets могут снова включить отключённого.
До постоянной блокировки нужно отдельно проверить reset-настройки и реальное
закрытие сессий. Текущий адаптер не обещает такой переход.

## Invoice Ninja recurring

После оплаты первого обычного счёта создаётся **новый черновик расписания**, а
не клон оплаченного invoice и не ещё один счёт за тот же период. Простой POST
`/api/v1/recurring_invoices` не выпускает обычный invoice.

Поля контракта: `frequency_id:5` (месяц), `next_send_date` из `Payment.date` плюс
календарный месяц, `due_date_days:"on_receipt"`, `auto_bill:"off"`,
`remaining_cycles:-1`, явный режим налогов и одна строка реального продукта.
`status_id`, `currency_id`, `first_invoice_id`, `send_now`, clone / payment / email
флаги не отправляются. Эти связи хранятся в будущем локальном журнале.
`BuildRecurringDraft` отклоняет будущую дату платежа. `RecurringClient` имеет
отдельные `CreateDraft`, `Get`, `Find` и `StartFirst`, но не stop / resume.
У recurring-черновика `balance == amount > 0`: это прогнозная сумма цикла,
а не признак оплаты. Правило нулевого balance обычного draft здесь неприменимо.
История `last_sent_date` читается как фактический SQL / Carbon datetime; для
первого запуска она должна быть пустой.

`"0"` для due-date не означает надёжно тот же день; `on_receipt` формирует срок
на дату фактического выпуска. Currency берётся из эффективных настроек клиента.
Создание может взаимодействовать с компанией `update_products`; настройки
каталога и автоматизации установки нужно проверить перед реальным тестом.

Черновик имеет статус `1`. Первый `start` через bulk с одним ID переводит его в
active `2`; paused — `3`, completed — `4`. Старт сам не выпускает invoice и не
двигает дату. Но активное due-расписание подбирает hourly cron, поэтому перед
стартом проверяются не только клиентская дата, но и фактический UTC datetime
запуска. Просроченное неизменяемое намерение останавливается, не переносится молча.

Send time зависит от настроек клиента; значение 0 означает UTC-полночь, не
обязательно локальную. Следующие месяцы исходный код считает с `addMonthNoOverflow`:
31 января → 28 февраля → 28 марта, без автоматического возврата к 31-му.
Эти условия, даты 29–31 и due date ещё нужно испытать на установленном сервисе.

Полный поиск выполняется по `client_id`, всем lifecycle-статусам и конечной
пагинации, с локальным сравнением приватного маркера. Private-notes filter
не поддерживается. Отсутствие / неполный список не разрешают второй create.
Неизвестный исход первого `start` требует проверки полного расписания и
возможных сгенерированных эффектов; одного active-статуса недостаточно.
Stop не отменяет уже подобранную / выполняемую генерацию.

## Что остаётся до выдачи доступа

Нужны durable flow активации, порядок и восстановление шагов, новый GET полной
оплаты перед эффектами, сохранение привязок, защита конфигурации при постановке /
доставке outbox, реальные тесты S-UI / recurring на выделенной записи и проверка
sing-box. Меню продолжает не выдавать персональную подписку, а локальный
`desired_access` не меняется. Автоматический импорт старых клиентов — отдельный этап.
