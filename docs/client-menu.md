# Клиентское меню

Меню работает при `TELEGRAM_ENABLED=true`, независимо от включения записи
`REGISTRATION_ENABLED`. При обычном старте обращения к Invoice Ninja нет.
Клавиатура постоянная, содержит только четыре текстовые кнопки; callback и
внешние идентификаторы в её данных не используются.

| Кнопка | Команда | Ответ |
| --- | --- | --- |
| Текущий счёт и реквизиты | `/invoice` | Сохранённый текущий счёт, сумма, остаток, срок, invitation link и реквизиты |
| Состояние подписки | `/status` | Последнее сохранённое состояние в БД бота, не проверка текущего доступа S-UI |
| Моя конфигурация | `/config` | По умолчанию закрыта; отдельный защищённый пилот выдачи после проверки права |
| Инструкция подключения | `/help` | Встроенная общая инструкция sing-box без персональных ссылок |

`/menu` открывает меню. Первый `/start` атомарно сохраняет регистрацию,
задание первого счёта и приветствие с клавиатурой. Если запись регистрации
выключена, задание остаётся в очереди, но меню отвечает. Повторный `/start`
открывает существующую запись и не создаёт второго задания или счёта.
Инструкция доступна без регистрации; остальные действия предлагают `/start`.

## Границы текущего этапа

[Проверка ручных платежей](payments.md) включается отдельно. Статус показывает
её последнее наблюдение и отметку ручной перепроверки, если доказательство
изменилось. [Пилот первой активации](activation.md) включается отдельно; меню
не вызывает write-адаптеры. Ни локальное `active`, ни один `paid` / нулевой
остаток Invoice Ninja не разрешают выдачу конфигурации. [Защищённая выдача](configuration-delivery.md)
включается отдельно и только для первого собственного оплаченного периода.
Меню сохраняет несекретное намерение; полные GET-проверки, личный `getChat` и
повторная авторизация выполняются в outbox перед отправкой. До включения либо
при несоблюдении условий `/config` не раскрывает ссылку. Отключение доступа
при просрочке ещё не реализовано.

Обычная инструкция не содержит персональных реквизитов и встроена в бинарник.
Она не заменяет будущую проверку импорта конкретного JSON-профиля в установленном
клиенте sing-box.

## Чтение счёта

Внутри обработчика меню только `/invoice` или соответствующая кнопка читают Invoice Ninja.
Защищённый `/config` читает провайдеров позднее, в отдельном outbox-dispatch. Нужны
`INVOICE_NINJA_BASE_URL` и `INVOICE_NINJA_API_TOKEN`; используется отдельная
read-only возможность `Client`, без конструирования write-клиента. Если одно
или оба значения отсутствуют, локальные действия остаются доступны, а чтение
счёта сообщает о недоступности. При двух заданных значениях неправильный URL
или токен с недопустимыми символами отклоняется до запуска webhook.

Источники выбора счёта — только сохранённые привязки клиента. Запросы:

1. `GET /api/v1/clients/{сохранённый ID}`: API ID должен совпасть, `id_number`
   обязан точно равняться ID отправителя, клиент не должен быть архивным / удалённым.
2. `GET /api/v1/invoices/{сохранённый ID}`: проверяются ID счёта, `client_id`,
   состояние, суммы, календарные даты и HTTPS invitation link.

Оба GET делят общий бюджет 1,5 секунды, оставляя время для фиксации ответа
в пределах общего пятисекундного deadline webhook. Ошибки удалённого сервиса
не раскрываются клиенту: ставится безопасный ответ с предложением повторить
запрос. Ошибки БД и изменившаяся локальная привязка дают HTTP 503 для повторной
доставки Telegram.

При частичной оплате сумма к переводу равна текущему **остатку**, а не полной
сумме счёта. Суммы форматируются без `float64`. Старый неоплаченный счёт доступен
и в состоянии `overdue`. Черновик, отмена и сторно не содержат приглашения
перевести деньги. API-статус оплаты не подменяет подтверждение платежа.

Ответ отражает момент чтения, а не момент фактической доставки Telegram.
Перед переводом клиенту предлагается проверить актуальный остаток в самом
счёте. Меню не пересчитывает цену и не создаёт новый счёт.

`PAYMENT_PHONE`, `PAYMENT_BANK`, `PAYMENT_RECIPIENT` берутся из окружения. Для
меню они необязательны: при отсутствии телефона бот не придумывает реквизиты
и предлагает уточнить их у администратора. Для включения создания первого
счёта телефон по-прежнему обязателен. Список `REGISTRATION_EXCLUDED_TELEGRAM_IDS`
учитывается в меню даже при выключенном биллинге; исключённый пользователь
не вызывает API и не получает платёжных сведений, общая инструкция доступна.

## Авторизация и сохранение

Принимаются только личные сообщения, где `from.id` положителен и совпадает
с `chat.id`; сообщения ботов и групп не выполняют действий. Slash-команды
требуют Telegram entity `bot_command` с корректным offset / length и, если
задан `@username`, обращением к текущему боту. Параметры разрешены только для
`/start` deep links и не используются как идентификаторы. Другая команда
с аргументом или чужим ID игнорируется. Текстовые кнопки выбираются точным
сравнением; имя и username пользователя не участвуют в авторизации.

Внешние GET выполняются **вне транзакции**. Перед чтением проверяется повтор
update, а при фиксации повтор проверяется ещё раз под блокировкой бота. Для
нового update клиент и подписка блокируются, снимок привязок перечитывается
и сравнивается с использованным для ответа. При конфликте всё откатывается,
включая метаданные обработки. Для неизвестного `/start` отдельно доказывается,
что клиент и подписка созданы именно этой транзакцией.

Ответ и отметка update фиксируются вместе с регистрацией, когда она нужна.
Меню не использует FIFO операций регистрации: задание на ручной проверке
не блокирует инструкцию или повторное открытие счёта. После коммита ответ
доставляется через обычный outbox с его очередностью, арендой и cooldown.
При потере подтверждения доставки Telegram сообщение всё ещё может повториться.

Статус также читает флаг перепроверки из наблюдений оплаты миграции `007`.
Блокировка клиента и повторное чтение защищают этот флаг вместе с привязками.

Миграция `006_client_menu.sql` добавляет только `outbox.client_menu` с `false`
для старых сообщений. Флаг клавиатуры включён в неизменяемые данные сообщения:
его нельзя поменять повтором того же бизнес-ключа. Старые миграции не менялись.
Как и прежде, старый бинарник не запускается с неизвестной ему новой миграцией;
перед обновлением нужны резервная копия и проверка совместимости отката.

Проверки используют синтетический HTTP и отдельные схемы PostgreSQL/Neon.
Настоящие Telegram сообщения, операции создания Invoice Ninja и запросы
персональных подписок S-UI при разработке не выполнялись.
