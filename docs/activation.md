# Первая активация: этап 7b

В обычном режиме активация, наблюдение счетов и enforcement работают без
`ACTIVATION_ENABLED` и иных feature flags; настройте бизнес-параметры по
[инструкции обычного запуска](configuration.md), включая тариф, валюту и `TZ`.
Доступ к managed/private actor определяется доказанными provenance и политикой,
а не обязательным пилотным allowlist. Неизвестные результаты и permission
barriers остаются обязательными. Старые stage/pilot настройки ниже описывают
прежний этап и не являются обычными startup-инструкциями. Условия и ограничения
описаны в
[invoice-lifecycle.md](invoice-lifecycle.md). Lifecycle enforcement не
восстанавливает доступ после оплаты; импорт управляется отдельным строгим потоком.

Сам исполнитель не выдаёт персональную конфигурацию. Защищённый `/config`
описан в разделе [выдачи конфигурации](configuration-delivery.md). Импорт
прежних аккаунтов, продления, отключение / closeSessions, stop / resume и
автоматическая компенсация частичных результатов не входили в исторический scope
этапа 7b. Текущий scope отключения при просрочке описан в
[invoice-lifecycle.md](invoice-lifecycle.md). Несопоставленные записи, включая
исключённые владельцем, не становятся управляемыми.

Не выполняйте реальные внешние записи без отдельного разрешения на выделенную
тестовую запись. Слияние PR и успешные CI не разрешают реальные POST, выдачу секретов или доставку
настоящим Telegram-получателям. Все проверки записи выполняются синтетическим HTTP
и в изолированных схемах Neon. Публичные контракты и ограничения адаптеров:
[activation-adapters.md](activation-adapters.md).

## Настройки и исторические параметры этапа 7b

Нужны уже настроенные Telegram и [проверка платежей](payments.md), отдельный
владелец / компания Invoice Ninja и одна база бота. Исходный клиент / первый
счёт должны иметь завершённый собственный журнал
[регистрации](registration.md). Произвольные внешние ID не являются таким журналом.

| Переменная | По умолчанию / требование |
| --- | --- |
| `ACTIVATION_WORKERS` | `1`, допустимо 1–4 |
| `ACTIVATION_POLL_INTERVAL` | `1s`, допустимо 100ms–1m |
| `ACTIVATION_HTTP_TIMEOUT` | `5s`, допустимо 1s–10s на запрос |
| `ACTIVATION_MAX_SUI_ACCOUNTS` | `1000`, допустимо 1–1000 полных клиентов |

Используются `INVOICE_NINJA_BASE_URL`, `INVOICE_NINJA_API_TOKEN`,
`INVOICE_NINJA_PRODUCT_ID`, `PAYMENTS_CURRENCY_ID`, `PAYMENTS_CURRENCY_CODE`, явное
`INVOICE_NINJA_INCLUSIVE_TAXES`, строго `INVOICE_NINJA_TELEGRAM_ID_FIELD=id_number`,
а также `SUI_BASE_URL`, `SUI_API_TOKEN` и `SUI_INBOUND_IDS`. `SUI_VERSION`
необязателен: по умолчанию используется поддерживаемая версия, которая всё равно
проверяется через API перед записью.
Границы страниц — `INTEGRATION_PAGE_SIZE` / `INTEGRATION_MAX_PAGES`.
S-UI поддерживается только 1.6.4, Invoice Ninja — 5.13.47. Источники версии
проверяются перед каждой записью, но не удостоверяют неизменность сборки.

`REGISTRATION_EXCLUDED_TELEGRAM_IDS` исключает actor до внешних GET / POST.
Настоящие ID, токены, имена
подписок и URL не помещают в Git, примеры, общий отчёт или логи.

Историческая настройка exclusive-writer обозначала отсутствие параллельных
внешних записей; она не является текущим обязательным startup-флагом. Все
экземпляры должны использовать одну БД и согласованную внутреннюю политику.
Гарантий CAS со стороны API нет. Настройки `update_products`, cron, очереди,
timezone и внешние автоматизации проверяйте перед разрешённым живым тестом.

## Откуда берётся работа

Обнаружение проверяет только собственную завершённую регистрацию и подтверждение
текущего **первого обычного** счёта. Подписка ещё ожидает первую активацию, локальных
S-UI / recurring-привязок и запроса доступа нет. Подтверждение принадлежит тому же
боту / клиенту / invoice / customer, совпадают hash доказательства и даты;
оба источника review должны быть чистыми.

Обнаружение ограничено доказанными managed actors и порциями до 50, не импортирует
записи и само не разрешает POST. Операция `activate_first_subscription` использует клиентский
FIFO общей очереди, но выборка отдельно проверяет bot ID. Отложенный или
неподдерживаемый старший переход не обходится. На клиента создаётся одна такая
операция; повторная оплата не создаёт второй первый цикл.

Новая миграция `008_first_activation.sql` добавляет flow, четыре шага,
неистекающий барьер записи и сохранённую S-UI-привязку. Прежние миграции не меняются.
Намерение ограничено 32 KiB компактного JSON / 64 KiB JSONB-представления; пробелы
PostgreSQL не делают ранее допустимое намерение нечитаемым. Очень большие записи
направляются на разбор до отправки, не усекутся молча.

## Порядок перехода

Один захват выполняет не больше одной внешней записи:

1. Создать новый **отключённый** S-UI-клиент со случайным именем / credentials.
2. Создать **draft** recurring на `Payment.date` плюс календарный месяц.
3. Включить только сохранённого S-UI-клиента, сохраняя его реквизиты / inbounds.
4. Выполнить первый `start` только сохранённого будущего recurring.
5. Заново прочитать точные внешние записи и полное подтверждение оплаты; атомарно
   сохранить локальные привязки, `active` / `desired_access`, завершение и outbox.

До нового recurring требуется полный конечный поиск по клиенту без чужих
расписаний, включая архив / удаление. Товар читается из Invoice Ninja, строка /
налоговый режим замораживаются. Счёт за уже оплаченный период не клонируется.
`frequency_id=5`, `due_date_days=on_receipt`, `auto_bill=off`, unlimited cycles;
`balance == amount > 0` у recurring-черновика не означает оплату.

Существующий результат каждого подтверждённого шага перечитывается перед
продолжением. В ответе создания recurring отдельно сохраняются точная сумма
и UTC-время первого запуска. Дальнейшие GET и первый start должны совпадать
именно с ними, а не только с новым снимком текущей попытки. Числовой ID, точное случайное имя и fingerprint полной config S-UI
выводятся из собственного зафиксированного создания, не из подписи или Telegram
имени. Неожиданно включённый аккаунт или активный recurring без подтверждённого
шага не принимаются за успех.

## Проверка перед каждым POST

У адаптеров есть отдельные методы `*Authorized`: они сначала выполняют свои
read-only проверки, затем вызывают последний callback. Обычные методы записи
в этом исполнителе не используются. В callback:

- заново выполняется полный GET-протокол `payments.Observe`: владелец, invoice,
  две полные инвентаризации платежей, повторные invoice / customer, точное cash
  покрытие и родная валюта;
- требуется тот же hash исходного подтверждения и неистёкший период;
- под локальными блокировками повторно проверяются привязки / provenance,
  обе review-отметки, политика и аренда;
- фиксируются новое неизменяемое намерение и единственное разрешение записи;
- POST допускается лишь после подтверждённого синхронного COMMIT нового намерения
  (`SET LOCAL synchronous_commit=on` не позволяет параметрам подключения ослабить
  гарантию сохранения журнала перед POST).

Доказательство из БД само по себе ничего не разрешает. Неавторитетная ошибка
GET / неполный или меняющийся список переносит работу, не объявляет платёж
отсутствующим. Несовместимый write-контракт / версия могут остановить flow для
разбора, но не инвалидируют оплату. Авторитетное изменение / возврат / потеря покрытия
останавливает активацию и делает исходное подтверждение sticky-review, не
переписывая старые суммы и даты.

Дата берётся из `Payment.date`, не из обработки или webhook. Уже истёкший период /
расписание останавливается без молчаливого переноса. После появления recurring
должны оставаться будущими и клиентская дата, и реальный UTC send datetime.
Проверки повторяются после ожидания разрешения БД. Непосредственно перед
COMMIT разрешения / завершения SQL также проверяет фактические часы против
минимума границы оплаченного периода и сохранённого UTC send datetime:
старый параметр `today` не разрешает закончить переход после истечения срока.

## Барьер записи, поколения и неизвестные результаты

Аренда защищает локальные изменения, **не останавливает уже отправленный HTTP**.
Поэтому барьер внешнего dispatch не истекает с арендой и не перехватывается новым
процессом. Он общий для активаций этой базы. Нормальный подтверждённый результат
освобождает барьер в той же транзакции, что подтверждает шаг; подтверждать может
только исходный `dispatch_attempt` с действующей арендой.

Дополнительно снимок получает монотонный `WriteEpoch` **до всех API-preflight**.
Каждое новое разрешение увеличивает epoch. Подготовка POST требует того же epoch
и свободного барьера. Если другой процесс успел записать и уже освободил барьер,
старые inventory / snapshot всё равно отвергаются. Простого mutex одного процесса
или проверки «барьер сейчас свободен» недостаточно.

Неизвестный COMMIT, потеря ответа, отмена после разрешения, падение между шагами
и просроченная аренда не дают новый POST. Любое уже существующее неподтверждённое
намерение означает ручную остановку. Положительный GET создания может помочь
разбору, но не доказывает, что старый отправитель / обработчик уже закончил работу;
по нему не освобождается барьер и не разрешается enable / start.

В этом этапе нет команды очистки sticky-review, повторного вооружения запроса
или снятия неизвестного барьера. Для будущего восстановления сначала потребуется
установить остановку старых отправителей и известный исход сервера. Прямое удаление
строк журнала или ручное обнуление барьера не являются поддерживаемым восстановлением.

## Частичный результат и сообщения

Подтверждённые шаги не повторяются. Например, после известного enable и ошибки
start аккаунт может оставаться включённым, хотя локальное завершение не произошло.
Автоматического отката / удаления / disable нет. Уведомление администраторам
предупреждает о возможном частичном результате, не утверждает, что доступ не менялся.

После всех шагов сообщения не содержат паролей или персональных ссылок и не
доказывают реальное соединение sing-box. Outbox атомарен с локальным завершением;
при неизвестной Telegram-доставке ровно одно сообщение всё ещё не гарантируется.
Меню показывает локальное состояние. Отдельный этап 7c заново проверяет право
на выдачу в момент доставки; локальное завершение активации не заменяет эту проверку.

Остановка отменяет API и новых исполнителей; известные результаты и retry / hold
используют один общий финальный DB-бюджет до 8 секунд на попытку. Сервис по-прежнему
имеет общий 10-секундный shutdown budget и закрывает БД после join исполнителей.

## Перед реальным включением

Нужны отдельно разрешённый тест полного цикла, проверка S-UI core / links /
протокола и подключения, реальные испытания защищённой доставки и Stage 1 / Stage 2
enforcement, проверка месяца 29–31 и timezone / cron. Нельзя считать успешный mock
или наличие локального `active` разрешением на широкий rollout.
