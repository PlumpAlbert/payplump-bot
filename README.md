# payplump-bot

Go-бот для Telegram, Invoice Ninja и S-UI: регистрация, счета, проверка оплаты,
активация, продление, отключение при просрочке и выдача личной конфигурации.

## Запуск в Docker / Komodo

1. Подготовьте приватный env-файл по [`.env.example`](.env.example): подключения
   к PostgreSQL, Telegram, Ninja и S-UI, ID продукта, реквизиты оплаты и таймзона.
2. Используйте [`compose.yaml`](compose.yaml). По умолчанию настройки берутся из
   `.env` рядом с Compose **на Docker-хосте**. Для другого пути задайте
   `PAYPLUMP_ENV_FILE`.
3. Остановите прежний экземпляр и выполните pull/deploy существующего стека.

**Подробная инструкция: [Docker / Komodo](docs/deployment.md).**

- Telegram по умолчанию работает через long polling: публичный URL не нужен.
- Валюта и налоговый режим читаются из настроек компании Ninja, если не заданы
  явно. Продукт выбирается по API `id`, не по названию.
- Точные версии Ninja/S-UI указывать не нужно. Бот проверяет фактические ответы
  API, а не совпадение номера релиза с одной строкой.
- Webhook Ninja необязательны. Пустые секреты отключают только HTTP-маршруты;
  периодическая сверка через API остаётся. Заданные секреты используются как есть.
- Не нужны пилотные allowlist, enable-флаги, номера ревизий, manifest,
  отдельный pgpass или запуск ручного release workflow.
- При первом скачивании образа GHCR package должен быть публичным либо Docker-хост
  должен иметь доступ к приватному package.

**Один токен Telegram — один экземпляр бота.** При переносе используйте ту же БД.
Обычный запуск автоматически принимает и обслуживает подходящих клиентов
настроенных панелей: это не режим проверки одного аккаунта. Перед обновлением
существующей БД сделайте резервную копию; миграции применяются при старте.

CI публикует `ghcr.io/plumpalbert/payplump-bot:main` и тег commit, но не
перезапускает Komodo. Новый образ применяется через pull/redeploy существующего
стека. Для точного выбора сборки можно задать `PAYPLUMP_IMAGE` с digest.

## Настройки и ошибки

Полный список: [configuration.md](docs/configuration.md).
Приложение читает окружение процесса и само не загружает `.env`; Docker Compose
передаёт файл через `env_file`. Не публикуйте заполненные файлы и не выводите
обычный `docker compose config`, который может раскрыть секреты.

`INVOICE_NINJA_BASE_URL` задаётся без `/api/v1`, `SUI_BASE_URL` — без `/apiv2`.
Нестандартный установочный подпуть сервиса сохраняется. Для PostgreSQL можно
использовать `DATABASE_URL` или отдельные `PG*` без ручного URL-кодирования пароля.
`TZ` задаёт расчётную таймзону, например `Europe/Moscow` или `UTC`.

Ошибки внешних API указывают этап и безопасную причину: HTTP-статус, категорию
ошибки соединения или недостающее поле ответа. Токены и тела ответов в ошибки
не включаются. Ошибка Ninja больше не называется ошибкой Telegram.

Из старых env-файлов удалите этапные флаги, пилотные allowlist, ручные
`*_REVISION` и `IMPORT_VERIFY_*`: обычный сервис сам устанавливает свои политики.
`REGISTRATION_EXCLUDED_TELEGRAM_IDS` остаётся явным списком исключений.

## Что делает бот

- Принимает личные Telegram-команды и меню; режим webhook выбирается только
  при заданном `TELEGRAM_WEBHOOK_URL`.
- Создаёт клиента и первый счёт, сверяет оплату по API Ninja.
- Активирует и продлевает S-UI доступ, обрабатывает последующие счета и просрочку.
- Автоматически проверяет и импортирует подходящих существующих клиентов.
- Выдаёт конфигурацию владельцу после проверки прав и текущего состояния.
- Предоставляет администраторам рассылки с предпросмотром и подтверждением.
  Сам запуск приложения рассылку не делает.

Проверки владельца счёта, сумм, валюты, прав доступа и повторных операций
сохраняются. Неизвестный результат внешней записи не переигрывается вслепую.
Синтетические тесты не заменяют проверку установленного сервиса и банковского
поступления.

## Разработка и проверки

Нужны Go 1.27.2; для интеграционных тестов — отдельная PostgreSQL 17.

```sh
go mod download
go mod verify
go vet ./...
go test -race ./...
CGO_ENABLED=0 go build -trimpath -ldflags='-s -w' -o bin/payplump ./cmd/payplump
```

`go test ./...` не требует рабочей БД и API-токенов. Полные PostgreSQL-тесты
запускайте только на отдельной тестовой БД с правом `CREATE SCHEMA`:

```sh
go test -race -tags=integration -count=1 -timeout=60m ./internal/postgres ./cmd/payplump
```

`TEST_DATABASE_URL` имеет приоритет над `PG*`. Каждый integration-тест создаёт
свою схему. Обычный PR CI запускает тесты на disposable loopback PostgreSQL 17;
Neon используется только при отдельном ручном `full_neon=true`.

Для разработки есть отдельный `compose.dev.yaml`; он не является шаблоном
рабочего развёртывания. Сборка использует distroless/nonroot, миграции встроены
в бинарник. Healthcheck: `payplump healthcheck` проверяет `/readyz`, `/livez`
проверяет сам HTTP-процесс.

`payplump serve-health` выключает внешние функции, но применяет миграции и
startup fences. Используйте его **только с disposable БД**, не с рабочей.
`payplump check-integrations` делает только GET к настроенным Ninja/S-UI, не
открывает БД и не меняет провайдеров; это диагностическая команда, не обязательный
шаг установки.
