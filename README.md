# payplump-bot

Go-сервис для Telegram, Invoice Ninja и S-UI. Бизнес-правила и критерии
приёмки находятся в [spec.md](spec.md). Операторские инструкции: [резервное
копирование и восстановление](docs/backup-restore.md), [подготовка выпуска](docs/release.md)
(инструменты готовы и прошли review; exact-HEAD CI pending, выпуск не запускался)
и [operator tools](docs/operator.md).

Сейчас реализованы HTTP healthcheck, корректная остановка, PostgreSQL с
встроенными миграциями, календарные правила и приём личного Telegram `/start`
через защищённый webhook с атомарной регистрацией и защитой от повторов.
Добавлены очередь операций и outbox для долговечной доставки Telegram-сообщений.
Добавлены read-only адаптеры Invoice Ninja и S-UI и отдельная команда проверки
интеграций. Обработчик регистрации умеет создать клиента и первый счёт Invoice
Ninja, но **выключен по умолчанию**. До оплаты он не создаёт recurring, не выдаёт
подписку и не меняет S-UI. Реальные операции записи ещё не проверены; условия
включения и восстановления описаны в [docs/registration.md](docs/registration.md).
Клиентское меню отвечает независимо от включения биллинга; выдача личной
конфигурации требует отдельного включения и повторной проверки права. Независимый opt-in обработчик оплаты проверяет
ручные платежи через GET и сохраняет даты, но не включает доступ и recurring.
Адаптеры S-UI / recurring имеют отдельный default-off исполнитель первой
активации: `ACTIVATION_ENABLED` требует явного пилотного allowlist до 20 ID,
оплаты и эксклюзивного writer-режима. `CONFIGURATION_DELIVERY_ENABLED` отдельно
включает защищённую выдачу по запросу только в первом оплаченном периоде.
Отдельные Stage 1 / Stage 2 для управляемых счетов реализованы, но выключены
по умолчанию: Stage 2 с начала следующего локального календарного дня после
канонического `invitations[].sent_date` приостанавливает recurring, отключает
привязанную S-UI-запись и запрашивает `closeSessions`. Используется общий writer-guard/epoch;
неизвестные записи не переигрываются. `due_date` Invoice Ninja не переписывается.
Восстановление после оплаты, импорт старых клиентов и live rollout не выполнены.
Условия и ограничения: [docs/invoice-lifecycle.md](docs/invoice-lifecycle.md),
этап первой активации: [docs/activation.md](docs/activation.md); контракты API:
[docs/activation-adapters.md](docs/activation-adapters.md).

Календарные расчёты используют локальную таймзону сервера: Go определяет её
из `TZ` или `/etc/localtime`. Если данные таймзоны недоступны, используется
UTC. У контейнера собственная таймзона; при необходимости задайте `TZ` в
окружении контейнера. Таймзона хоста не передаётся в контейнер автоматически.

## Локальная разработка

Нужны Go **1.27.2**, PostgreSQL **17** и Python 3 для smoke-проверки.
Docker нужен, если PostgreSQL запускается в контейнере.

В облачном окружении Go установлен отдельно; для каждого нового shell:

```sh
export PATH=/workspace/.cloud-tools/go1.27.2/bin:$PATH
export GOCACHE=/workspace/.cloud-cache/go-build
export GOPATH=/workspace/.cloud-cache/gopath
export DOCKER_CONFIG=/workspace/.cloud-cache/docker
mkdir -p "$DOCKER_CONFIG"
cd /workspace/payplump-bot
```

Из корня репозитория:

```sh
go mod download
go test ./...
CGO_ENABLED=0 go build -trimpath -ldflags='-s -w' -o bin/payplump ./cmd/payplump
```

Приложение читает переменные процесса, `.env` автоматически не загружает.
[.env.example](.env.example) содержит пустой шаблон; значения задаются вне Git.
Для подключения без URL явно задайте `PGHOST`, `PGUSER`, `PGDATABASE`.
Драйвер также читает `PGPORT`, `PGPASSWORD` и `PGSSLMODE` непосредственно из
окружения, поэтому символы в пароле не нужно кодировать для URL. По умолчанию
драйвер использует порт 5432 и `sslmode=prefer`; для CI все настройки задаются
явно. `DATABASE_URL` остаётся альтернативой: явно указанные в нём поля имеют
приоритет над соответствующими `PG*`.

Для отдельной локальной БД скопируйте `.env.example` в `.env` и заполните
`PGUSER`, `PGDATABASE`, `PGPASSWORD`, `PGSSLMODE`. Затем из корня репозитория:

```sh
docker compose -f compose.dev.yaml up -d --wait db
```

Compose читает `.env` и передаёт параметры контейнерам. Для запуска бинарника
на хосте задайте те же переменные в окружении своего shell, указав в `PGHOST`
адрес опубликованной БД, а в `PGPORT` — её опубликованный порт (по умолчанию
Compose публикует `127.0.0.1:15432`). Для этой локальной БД без TLS задайте
`PGSSLMODE=disable`. После настройки окружения:

```sh
./bin/payplump
```

При старте применяются миграции в одной транзакции под advisory lock.
Роль БД должна иметь право создавать таблицы и индексы. Применённые миграции
нельзя редактировать: проверяются SHA-256; изменения схемы добавляются новыми
файлами. Бинарник отказывается стартовать с неизвестной ему версией миграций.
План миграций и совместимость отката нужно проверять до рабочего обновления.

В другом терминале `./bin/payplump healthcheck` проверяет `/readyz` с таймаутом
3 секунды и возвращает ненулевой код при ошибке. При другом адресе сервера
задайте `HEALTHCHECK_URL`. `/livez` проверяет HTTP-процесс, `/readyz` — доступность
PostgreSQL с таймаутом 2 секунды; детали ошибок БД в HTTP-ответ не попадают.
`DB_MAX_CONNS` задаёт размер пула: по умолчанию 4, допустимо 1–64.
SIGINT/SIGTERM дают общий срок до 10 секунд на завершение HTTP-запросов,
обработчиков регистрации и фоновых доставок перед закрытием пула БД.

## Приём Telegram `/start` через webhook

Telegram по умолчанию выключен. Для включения задайте окружение процесса
(для Compose — значения в локальном `.env`, исключённом из Git):

| Переменная | Назначение |
| --- | --- |
| `TELEGRAM_ENABLED` | `true` включает webhook; по умолчанию `false` |
| `TELEGRAM_BOT_TOKEN` | Токен отдельного тестового бота из безопасных настроек секретов |
| `TELEGRAM_ADMIN_IDS` | Один или несколько положительных Telegram ID через запятую |
| `TELEGRAM_WEBHOOK_URL` | Публичный HTTPS URL с путём `/telegram/webhook`, например `https://bot.example.com/telegram/webhook` |
| `TELEGRAM_WEBHOOK_SECRET` | Отдельный случайный секрет для проверки входящих запросов; 1–256 символов `A-Z`, `a-z`, `0-9`, `_`, `-` |

При включении все перечисленные значения обязательны. Используйте длинный
случайный webhook-секрет, отличный от токена бота; он должен быть доступен
приложению для сравнения с заголовком `X-Telegram-Bot-Api-Secret-Token`.
Административные функции появятся позднее; личная регистрация доступна любому
пользователю, как предусмотрено ТЗ. Для намеренно исключённых из биллинга
аккаунтов задайте `REGISTRATION_EXCLUDED_TELEGRAM_IDS` до включения записи.

Сначала подготовьте публичный HTTPS-адрес и reverse proxy, передающий
`POST /telegram/webhook` на HTTP-порт приложения с JSON-телом и заголовком
секрета. TLS завершается на reverse proxy; приложение слушает внутренний HTTP.
Для исходящей настройки webhook нужен HTTPS-доступ к `api.telegram.org`.

После открытия HTTP listener сервис вызывает `getMe` и `setWebhook` с URL,
секретом, `allowed_updates=["message"]`, `max_connections=1` и
`drop_pending_updates=false`. После успешной регистрации входящие сообщения
доставляются Telegram по HTTP; периодического опроса updates нет. Настройка
выполняется при каждом старте. Временные ошибки настройки повторяются с
задержкой 1–30 секунд, для `retry_after` — не меньше указанного Telegram.
Таймаут API-запроса — 10 секунд; постоянная ошибка API останавливает сервис.

До завершения настройки `/livez` отвечает, а `/readyz` и авторизованный webhook
возвращают 503. После настройки readiness проверяет также PostgreSQL.
При `TELEGRAM_ENABLED=false` маршрут webhook отсутствует, вызовы Telegram API
не выполняются. При остановке сервер завершает входящие запросы перед закрытием
БД; webhook в Telegram сохраняется для повторной доставки после перезапуска.

Endpoint проверяет секрет до разбора JSON и обращения к БД. Ограничение тела —
1 MiB, общий таймаут обработки — 5 секунд. HTTP 200 возвращается после коммита
результата, метаданных update и ответа outbox; для нового `/start` туда же входят
клиент, подписка и задание `register_client`.
Дубли возвращают 200 без повторной бизнес-обработки; при ошибке БД возвращается
503 для повтора доставки Telegram. Несовпадающий секрет даёт 403; некорректный
JSON, тип содержимого и слишком большое тело — 400, 415 и 413 соответственно.

Поддержаны `/start`, `/start@ИмяЭтогоБота` и аргумент после команды в личном
чате. Отправитель определяется по `from.id`, не по имени или username.
Групповые и неподдерживаемые updates фиксируются как обработанные без
регистрации клиента. Порядок ID не используется для отбрасывания сообщений:
повтор определяется по паре bot ID / update ID.

При переходе с прежней реализации остановите экземпляр с `getUpdates` перед
запуском новой версии. Миграция `003_telegram_webhook.sql` сохраняет обработанные
ID и связи, переименовывает реестр ботов и удаляет offset. Миграции `001` и `002`
не менялись; pending updates при настройке webhook не удаляются.

При выключенном `REGISTRATION_ENABLED` `/start` сохраняет регистрацию и отвечает
приветствием с меню, а задание первого счёта остаётся в очереди. При отдельном
включении обработчик создаёт первый счёт и ставит сообщения в outbox. Повторный
`/start` открывает меню без повторной регистрации. Публичный маршрут и доставку
настоящим ботом нужно отдельно проверить в тестовой интеграции этапа 2.

## Клиентское меню

При включённом Telegram доступны четыре текстовые кнопки и команды `/invoice`,
`/status`, `/config`, `/help`; `/menu` открывает клавиатуру. Инструкция доступна
без регистрации, а остальные действия предлагают `/start`. Внутри webhook только
запрос счёта читает Invoice Ninja по сохранённым привязкам с проверкой `id_number`
отправителя и владельца счёта; проверки конфигурации выполняются позже в outbox. При частичной оплате показывается остаток;
старый неоплаченный счёт можно открыть после отключения.

Статус сообщает о сохранённом состоянии БД, не о текущем соединении S-UI.
При отдельном включении проверки оплаты статус показывает последнюю проверенную
дату и необходимость перепроверки. По умолчанию `/config` закрыт даже для
локально активной записи. Отдельный пилот выдачи требует завершённую собственную
активацию, свежие GET-проверки и повторную авторизацию при отправке; личная ссылка
не хранится в outbox. Меню не блокируется остановленным заданием регистрации. Авторизация, бюджеты GET,
повторы, настройки и ограничения: [docs/client-menu.md](docs/client-menu.md).

## Долговечные задания и исходящие сообщения

Миграция `004_durable_work.sql` добавляет outbox и индексы очереди операций.
Миграции `001`–`005` не меняются. `005_registration_work.sql` добавляет журнал
регистрации, неизменяемые запросы шагов и `first_invoice_id`; `006_client_menu.sql`
сохраняет неизменяемый флаг клавиатуры в outbox. Выборка операций
требует явного списка типов: исполнитель `register_client` запускается только
при `REGISTRATION_ENABLED=true` после настройки Telegram. По одному клиенту одновременно арендуется только одно задание;
отложенное задание не пропускает вперёд более новые задания этого клиента.

Задания выбираются порциями не больше 100 и получают аренду от 1 секунды до
5 минут. Номер попытки служит монотонным идентификатором аренды: прежний
исполнитель после истечения срока или повторного захвата не может завершить
или перенести задание. Блокировки БД удерживаются только на время короткой
транзакции. Завершение операции и запись уведомлений в outbox атомарны.
Для первой регистрации каждый запрос Invoice Ninja предварительно записывается
в журнал. Неизвестный результат создания сверяется без повторного POST;
неизвестный результат выставления блокируется для ручной проверки. Наблюдение
платежей использует отдельную очередь, чтобы остановленное задание регистрации
не блокировало read-only проверки. Первая активация имеет отдельный opt-in
исполнитель и журнал, описанные в [docs/activation.md](docs/activation.md).

Доставка outbox запускается после успешной настройки webhook и проверки bot ID,
только при `TELEGRAM_ENABLED=true`. Она отправляет обычный текст без HTML/Markdown
и выбирает сообщения только своего бота. Ключ уведомления уникален в пределах
бота; повтор с тем же текстом и адресатом не создаёт новую доставку, изменение
данных под тем же ключом возвращает ошибку. Сообщения одного чата идут по порядку;
остальные адресаты обрабатываются независимо.

| Переменная | По умолчанию | Допустимо |
| --- | --- | --- |
| `OUTBOX_WORKERS` | `2` | `1`–`16` одновременных доставок |
| `OUTBOX_POLL_INTERVAL` | `1s` | `100ms`–`1m` между порциями |

Для обычных сообщений аренда доставки — 45 секунд, таймаут запроса Telegram — 10 секунд; на фиксацию
результата в БД отводится до 5 секунд. Временные ошибки повторяются с
экспоненциальной задержкой до 5 минут и небольшим случайным
разбросом; `retry_after` всегда задаёт нижнюю границу, даже если больше 5 минут.
При 429 пауза сохраняется в БД для всего бота и действует после перезапуска.
Постоянная ошибка адресата завершает только его доставку; ошибка авторизации
401 оставляет сообщения для повтора после восстановления настроек.
В БД сохраняются числовые коды ошибок, но не текст ответов API.

При остановке новые отправки прекращаются, текущие запросы отменяются,
известный результат сохраняется до закрытия БД. Оборванные аренды восстанавливаются
после истечения срока. При потере ответа после фактической отправки сообщение
может повториться: гарантия ровно одной доставки Telegram не обещается.
Защищённые configuration intents используют отдельный 30-секундный preflight,
одноразовое разрешение и терминальную ошибку без автоматического повтора;
неизвестный секрет оставляет барьер чата. Подробности ниже.
Сам запуск outbox не создаёт искусственных уведомлений; сообщения о счёте
записываются обработчиком регистрации в транзакции с её завершением.

## Административная рассылка

Рассылка выключена по умолчанию и требует отдельной настройки Telegram administrator IDs, явной монотонной `BROADCAST_POLICY_REVISION` и approval. Документированы команды, preview/rotation токенов, замороженная аудитория, отмена и durable progress в [docs/admin-broadcast.md](docs/admin-broadcast.md). Используется существующий outbox: ошибки адресатов независимы, доставка at-least-once, поэтому неизвестный исход может привести к повтору. Отключённый старт отзывает политику даже при выключенном Telegram. CI merge не является разрешением на доставку; реализация проверяется только на синтетическом HTTP, без production Invoice Ninja или S-UI.

## Проверка интеграций Invoice Ninja и S-UI

После настройки переменных из `.env.example` выполните:

```sh
set -a
. ./.env
set +a
CGO_ENABLED=0 go build -trimpath -o bin/payplump ./cmd/payplump
./bin/payplump check-integrations
```

Команда делает только GET-запросы, не открывает БД бота и не настраивает Telegram.
Она проверяет выбранный продукт, чтение счетов / платежей / recurring, страницы
клиентов, inbounds и публичный префикс подписки. JSON-отчёт содержит только
счётчики, результаты проверок и версии; ошибки идут в stderr. Имена, ID, токены,
контакты и ссылки подписок в отчёт не попадают.

Источник Telegram ID — явно выбранное поле Invoice Ninja, для текущей установки
`id_number`. Сравнение с `name` S-UI точное: подписи `desc` / `remark` не являются
идентификаторами. Сверка не импортирует клиентов и не меняет старые ссылки.
Несопоставленные аккаунты S-UI остаются вне управления; отсутствие совпадения
не доказывает отсутствие конфигурации. Счета, платежи и recurring читаются только
на первой странице, не больше двух записей каждого типа.

Проверены чтение Invoice Ninja 5.13.47 и структура S-UI 1.6.4. HTTP панели разрешён
внутри защищённой сети NetBird; HTTPS проверяет сертификат. Обычный старт сервиса
эту команду не запускает; фоновые API-вызовы требуют отдельного включения
регистрации, проверки платежей или пилота активации. CI использует синтетический HTTP и не требует API-токенов.
По запросу `/invoice` меню выполняет только GET даже при выключенной регистрации.
Подробности контрактов, ограничений, переменных и оставшихся испытаний:
[docs/integrations.md](docs/integrations.md).

## Операторские инструменты

`recovery-report` формирует read-only отчёт по локальным операциям и требует уже
применённую поддерживаемую схему. `import-plan` проверяет частный manifest без
изменений; `import-stage` с обязательным `--apply` записывает только неизменяемые
кандидаты в отдельные staging-таблицы и не включает клиентов/доступ.
`docs/operator.md` описывает ограничения, синтетический формат, восстановление,
шаблон Compose и безопасные измерения ресурсов. Эти команды не заменяют ручную
проверку владельцем и допуск в управляемый биллинг.

## Webhook Invoice Ninja и проверка оплаты

`PAYMENTS_ENABLED=false` по умолчанию. При включении отдельный защищённый
`POST /invoiceninja/webhook` сохраняет хеш JSON только как сигнал сверки.
Суммы, ID и даты из webhook не считаются доказательством. Периодический
исполнитель читает текущие управляемые счета и все страницы платежей клиента.

Для подтверждения нужны точные привязки, completed manual cash-платежи и
allocation, полностью покрывающие сумму в согласованной валюте. Дата берётся
из `Payment.date`, а не времени доставки. Кредиты, FX и частично возвращённые
источники не поддерживаются. Одного `paid` / нулевого остатка недостаточно.
Доказательство, даты и сообщения outbox фиксируются атомарно; повтор не создаёт
второго периода. Ошибка API только переносит проверку, не объявляет неоплату.

Сама проверка платежей не меняет доступ, конфигурацию или recurring. Миграция `007` сохраняет
наблюдения и очередь; старые миграции не менялись. События исходящего webhook,
особенности 5xx / 404, собственная валюта, ограничения и внедрение:
[docs/payments.md](docs/payments.md). Реальную доставку и тестовый платёж ещё
нужно отдельно согласовать и проверить.

## Пилот первой активации

`ACTIVATION_ENABLED=false` по умолчанию. При отдельном включении нужны
`ACTIVATION_EXCLUSIVE_WRITER=true`, приватный allowlist из 1–20 Telegram ID,
явные версии / налоговый режим и включённая проверка платежей. Исключённые ID
имеют приоритет. Исполнитель создаёт отключённый S-UI аккаунт и draft recurring,
затем включает и запускает только их, проверяя оплату заново перед каждым POST.
Миграция `008` сохраняет шаги, исходные суммы / UTC расписания, монотонный epoch
и барьер dispatch, который не снимается при истечении аренды.

Неизвестный результат требует ручного разбора, не повторного POST. Отдельный
Stage 2 реализован, но выключен по умолчанию; live-проверки не выполнены, поэтому
широкий rollout не готов. Протокол и ограничения:
[docs/invoice-lifecycle.md](docs/invoice-lifecycle.md) и
[docs/activation.md](docs/activation.md).

## Наблюдение счетов и отключение при просрочке

Stage 1 и Stage 2 реализованы как отдельные default-off исполнители. Stage 1
наблюдает managed recurring-счета через GET, сохраняет ledger/outbox и передаёт
текущий invoice существующей проверке платежа. Stage 2 работает только с текущим
управляемым счётом: с начала следующего локального календарного дня после
канонического `invitations[].sent_date` он приостанавливает recurring, отключает
S-UI по сохранённой привязке и запрашивает `closeSessions`. `due_date` Invoice Ninja не
меняется. Записи защищены общим неистекающим guard и epoch; неизвестный исход
не переигрывается. Автоматического восстановления после оплаты, записей для
email reminders, импорта старых клиентов и live rollout здесь нет. В этой
итерации review fixes новые или изменённые PostgreSQL integration tests только
скомпилированы; runtime-запуска не было. В базовом состоянии PR17 ранее был
успешный CI на Neon, но он не подтверждает исправленную ветку или live-совместимость.
Подробности: [docs/invoice-lifecycle.md](docs/invoice-lifecycle.md);
контракты адаптеров: [docs/lifecycle-adapters.md](docs/lifecycle-adapters.md).

## Защищённая выдача конфигурации

`CONFIGURATION_DELIVERY_ENABLED=false` по умолчанию. `/config` может отправить
личную JSON-подписку только самому владельцу, в первом оплачиваемом периоде,
после свежих проверок оплаты, S-UI, recurring и личного Telegram-чата. Нужны
тот же приватный пилотный allowlist, HTTPS-база подписки и явная монотонная
`CONFIGURATION_POLICY_REVISION`. Обычного `active` или нулевого остатка мало.

В outbox хранится только несекретное намерение. Ссылка появляется в памяти
после одноразового durable-разрешения; предпросмотр отключён. Ошибка такого
запроса не запускает автоматический повтор. Неизвестная отправка оставляет
неистекающий барьер для новых секретов этого чата, но не блокирует обычное меню.
Выключенный старт отзывает новые разрешения в БД даже без Telegram; уже
переданный запрос или раскрытую ссылку отозвать этим нельзя.

Миграция `009`, условия повторного включения, границы отзыва и проверки:
[docs/configuration-delivery.md](docs/configuration-delivery.md). Реальные
Telegram-доставка, импорт и связь sing-box ещё требуют отдельного согласия.

## Проверки

```sh
go vet ./...
go mod verify
go test -race -tags=integration -count=1 -timeout=40m ./...
python3 scripts/smoke.py
```

Интеграционные тесты требуют отдельную тестовую PostgreSQL 17 и право CREATE
SCHEMA. Каждый тест создаёт и удаляет собственную схему; `TEST_DATABASE_URL`
позволяет явно указать БД и имеет приоритет над `PG*`. Не запускайте эти тесты
на рабочей БД. `go test ./...` проверяет код без БД. Smoke-проверка запускает
бинарник и применяет миграции в схеме приложения, поэтому ей также нужна только
отдельная тестовая БД.

Обычный PR в CI использует быстрые проверки без database credentials, затем
полный integration suite и smoke на disposable loopback PostgreSQL 17.
Neon запускается только отдельным ручным `workflow_dispatch` с
`full_neon=true` через GitHub Environment `test`. Время выполнения не
гарантируется. Интеграционные тесты проверяют миграции, очереди, повторы,
конкуренцию и календарные границы; Telegram API тестируется локальным HTTP.
CI и smoke принудительно выключают внешние записи, Telegram и выдачу, поэтому
реальные токены внешних API не нужны.

## PostgreSQL в GitHub Actions

Обычный PR не требует database secrets. Loopback job может задавать synthetic
credentials для disposable PostgreSQL; это только локальные тестовые значения,
не credentials рабочей БД или Neon.

Для ручного `workflow_dispatch` с `full_neon=true` настройте GitHub Environment
`test`. Задайте Variables и Secret:

| Имя | Назначение |
| --- | --- |
| `PGHOST` | Direct endpoint Neon, без `-pooler` |
| `PGPORT` | `5432` |
| `PGDATABASE` | Отдельная тестовая база |
| `PGUSER` | Роль с правом `CREATE SCHEMA` |
| `PGSSLMODE` | `require` |
| Secret `PGPASSWORD` | Пароль тестовой роли |

Используйте только отдельную тестовую БД / ветку. Интеграционные тесты создают
собственные схемы, smoke использует отдельную схему. Передавайте пароль через
Secret, не помещайте его в Variables, YAML или URL.

## Контейнер для разработки

```sh
VCS_REF=$(git rev-parse HEAD) docker compose -f compose.dev.yaml up --build --wait
docker compose -f compose.dev.yaml exec app /payplump healthcheck
docker compose -f compose.dev.yaml logs app
docker compose -f compose.dev.yaml stop app
docker compose -f compose.dev.yaml up -d --wait
```

В текущем облачном окружении сборщику нужны сетевой прокси и доверенный
CA bundle хоста. Их можно передать только на время сборки, не сохраняя
в образе или исходниках:

```sh
docker build --network=host \
  --add-host "proxy:$(getent ahostsv4 proxy | awk 'NR == 1 {print $1}')" \
  --build-arg HTTP_PROXY --build-arg HTTPS_PROXY --build-arg NO_PROXY \
  --secret "id=build_ca,src=$SSL_CERT_FILE" \
  --build-arg VCS_REF="$(git rev-parse HEAD)" -t payplump:dev .
docker compose -f compose.dev.yaml up --no-build --wait
```

Проверки TLS и `go.sum` при этом включены. За пределами этого окружения
обычно достаточно стандартной команды Compose выше. `DOCKER_CONFIG` из
раздела облачной настройки нужен, поскольку домашний каталог здесь read-only.

Локальная сборка использует многоэтапный Dockerfile: Go с `CGO_ENABLED=0`,
финальная база `gcr.io/distroless/static-debian13:nonroot`. Обе базы закреплены
по digest; миграции встроены в бинарник, сертификаты и tzdata входят в базу.
Сервис работает от UID
65532 с read-only файловой системой. Docker healthcheck вызывает подкоманду
самого бинарника. HTTP опубликован только на `127.0.0.1:8080`, PostgreSQL —
на `127.0.0.1:15432`. Переменные `PAYPLUMP_HTTP_PORT` и `PAYPLUMP_DB_PORT`
позволяют выбрать другие локальные порты; задавайте их одинаково во всех
командах Compose. Остановите ранее запущенную тестовую БД или выберите
другой порт, чтобы избежать конфликта.

`compose.dev.yaml` предназначен только для разработки: локальный тег
`payplump:dev`, без реестра и рабочих интеграций. PostgreSQL требует пароль
из окружения; `trust` не используется. Данные
сохраняются в volume; `docker compose -f compose.dev.yaml down` удаляет
контейнеры, но сохраняет volume. Добавление `--volumes` удаляет данные.
Новые значения `POSTGRES_*` применяются при инициализации пустого volume.
Если volume создан раньше, роль и пароль нужно обновить в существующей БД
либо использовать отдельный новый Compose project/volume; изменение `.env`
не меняет пароль в уже созданной базе.

Лимиты 128 MiB для приложения, 256 MiB для БД, `GOMEMLIMIT=96MiB`, 1 CPU
и ротация логов ограничивают локальное окружение. Это начальные значения
для разработки; они ещё не проверены на бизнес-нагрузке и не являются
рекомендацией для VPS. Рабочий выпуск должен использовать digest готового
образа, а не локальную сборку или тег `dev`. Публикация в реестр и развёртывание
Komodo здесь не выполняются.

## План реализации

Пошаговый план с чекбоксами, выполненной основой, зависимостями этапов и
покрытием критериев приёмки — в [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md).
Приём `/start`, очереди, чтение интеграций, первый счёт, меню, наблюдение оплаты,
первая активация, защищённая выдача и default-off Stage 1 / Stage 2 реализованы.
Stage 2 не восстанавливает доступ после оплаты. Импорт старых клиентов, live
проверки и рабочий rollout остаются невыполненными; синтетические проверки не
подменяют испытания на установленных сервисах.
