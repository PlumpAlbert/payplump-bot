# payplump-bot

Go-сервис для Telegram, Invoice Ninja и S-UI. Бизнес-правила и критерии
приёмки находятся в [spec.md](spec.md).

Сейчас реализованы HTTP healthcheck, корректная остановка, PostgreSQL с
встроенными миграциями, календарные правила и приём личного Telegram `/start`
через long polling с атомарной регистрацией и сохранением offset.
Invoice Ninja и S-UI ещё не подключены; сервис не выставляет счета,
не выдаёт подписки и не меняет доступ.

Календарные расчёты используют локальную таймзону сервера: Go определяет её
из `TZ` или `/etc/localtime`. Если данные таймзоны недоступны, используется
UTC. У контейнера собственная таймзона; при необходимости задайте `TZ` в
окружении контейнера. Таймзона хоста не передаётся в контейнер автоматически.

## Локальная разработка

Нужны Go **1.27.2**, PostgreSQL **17** и Python 3 для smoke-проверки.
Docker нужен, если PostgreSQL запускается в контейнере.

В облачном окружении Go установлен отдельно; для каждого нового shell:

```sh
export PATH=/workspace/.cloud-tools/go1.27.2/bin:$PATH
export GOCACHE=/workspace/.cloud-cache/go-build
export GOPATH=/workspace/.cloud-cache/gopath
export DOCKER_CONFIG=/workspace/.cloud-cache/docker
mkdir -p "$DOCKER_CONFIG"
cd /workspace/payplump-bot
```

Из корня репозитория:

```sh
go mod download
go test ./...
CGO_ENABLED=0 go build -trimpath -ldflags='-s -w' -o bin/payplump ./cmd/payplump
```

Приложение читает переменные процесса, `.env` автоматически не загружает.
[.env.example](.env.example) содержит пустой шаблон; значения задаются вне Git.
Для подключения без URL явно задайте `PGHOST`, `PGUSER`, `PGDATABASE`.
Драйвер также читает `PGPORT`, `PGPASSWORD` и `PGSSLMODE` непосредственно из
окружения, поэтому символы в пароле не нужно кодировать для URL. По умолчанию
драйвер использует порт 5432 и `sslmode=prefer`; для CI все настройки задаются
явно. `DATABASE_URL` остаётся альтернативой: явно указанные в нём поля имеют
приоритет над соответствующими `PG*`.

Для отдельной локальной БД скопируйте `.env.example` в `.env` и заполните
`PGUSER`, `PGDATABASE`, `PGPASSWORD`, `PGSSLMODE`. Затем из корня репозитория:

```sh
docker compose -f compose.dev.yaml up -d --wait db
```

Compose читает `.env` и передаёт параметры контейнерам. Для запуска бинарника
на хосте задайте те же переменные в окружении своего shell, указав в `PGHOST`
адрес опубликованной БД, а в `PGPORT` — её опубликованный порт (по умолчанию
Compose публикует `127.0.0.1:15432`). Для этой локальной БД без TLS задайте
`PGSSLMODE=disable`. После настройки окружения:

```sh
./bin/payplump
```

При старте применяются миграции в одной транзакции под advisory lock.
Роль БД должна иметь право создавать таблицы и индексы. Применённые миграции
нельзя редактировать: проверяются SHA-256; изменения схемы добавляются новыми
файлами. Бинарник отказывается стартовать с неизвестной ему версией миграций.
План миграций и совместимость отката нужно проверять до рабочего обновления.

В другом терминале `./bin/payplump healthcheck` проверяет `/readyz` с таймаутом
3 секунды и возвращает ненулевой код при ошибке. При другом адресе сервера
задайте `HEALTHCHECK_URL`. `/livez` проверяет HTTP-процесс, `/readyz` — доступность
PostgreSQL с таймаутом 2 секунды; детали ошибок БД в HTTP-ответ не попадают.
`DB_MAX_CONNS` задаёт размер пула: по умолчанию 4, допустимо 1–64.
SIGINT/SIGTERM дают HTTP-серверу до 10 секунд на завершение запросов.

## Приём Telegram `/start`

Polling по умолчанию выключен. Для включения задайте окружение процесса
(для Compose — значения в локальном `.env`, исключённом из Git):

| Переменная | Назначение |
| --- | --- |
| `TELEGRAM_ENABLED` | `true` включает polling; по умолчанию `false` |
| `TELEGRAM_BOT_TOKEN` | Токен отдельного тестового бота из безопасных настроек секретов |
| `TELEGRAM_ADMIN_IDS` | Один или несколько положительных Telegram ID через запятую |

При включении обязательны токен и хотя бы один ID администратора. Список
администраторов подготовлен для следующих административных функций; личная
регистрация доступна любому пользователю, как предусмотрено ТЗ. Клиент
использует `https://api.telegram.org`; окружению нужен HTTPS-доступ к этому
домену. Значение токена не следует помещать в исходники или сообщения об ошибках.

Бот должен работать в одном экземпляре с long polling и без активного webhook.
Сервис не удаляет существующий webhook автоматически. Он проверяет `getMe`,
читает сообщения порциями до 100 updates с long-poll timeout 30 секунд и
HTTP timeout 40 секунд. Временные ошибки повторяются с задержкой 1–30 секунд,
для `retry_after` задержка не меньше указанной Telegram. Ошибки авторизации
и конфликт polling / webhook прекращают работу сервиса с ненулевым кодом.

Поддержаны `/start`, `/start@ИмяЭтогоБота` и аргумент после команды в личном
чате. Отправитель определяется по `from.id`, не по имени или username.
Групповые, неподдерживаемые и некорректные сообщения не регистрируют клиента,
но обрабатываются так, чтобы очередь не застревала на них.

Новая миграция `002_telegram_updates.sql` хранит checkpoint отдельно для
каждого bot ID и метаданные обработанных updates без текста сообщений / токена.
Регистрация, долговечное задание `register_client`, отметка обработки и offset
коммитятся вместе. Следующий запрос подтверждает Telegram только сохранённый
offset; ошибка БД оставляет update доступным для повтора. После перезапуска
используется checkpoint из БД; повторный `/start` использует прежнего клиента.
Checkpoint старше 24 часов сбрасывается на ноль с учётом срока хранения updates
в Telegram и возможной смены диапазона ID после долгого простоя.

На этом этапе `/start` сохраняет регистрацию, но **ответы в Telegram ещё не
отправляются**. Доставка уведомлений через outbox, меню и обработчик
`register_client` появятся в следующих этапах. `/readyz` пока проверяет только
PostgreSQL; успешный healthcheck не подтверждает связь с Telegram.

## Проверки

```sh
go vet ./...
go mod verify
go test -race -tags=integration -count=1 ./...
python3 scripts/smoke.py
```

Интеграционные тесты требуют отдельную тестовую БД и права CREATE SCHEMA.
Каждый тест создаёт свою схему и удаляет её после выполнения. Тесты читают
`PG*` из окружения; `TEST_DATABASE_URL` позволяет указать отдельную тестовую
БД и имеет приоритет. Без явного адреса, пользователя и БД запуск с
`-tags=integration` завершается ошибкой.
Обычный `go test ./...` проверяет только код без БД.
Smoke-проверка запускает настоящий бинарник дважды и применяет миграции в
основной схеме БД приложения (`PG*` или `DATABASE_URL`); используйте только
тестовую БД.

Проверяются конкурентная регистрация одного Telegram ID без дублей,
отсутствие доступа до оплаты, повтор после переподключения, сохранение
завершённого задания, откат при ошибке очереди, миграции и календарные границы.
Ограничение следующего месяца последним днём для 29–31 чисел покрыто тестами,
но совместимость с установленным Invoice Ninja ещё требуется проверить.
CI выполняет те же проверки на PostgreSQL 17 и собирает статический бинарник.
Telegram API проверяется локальным HTTP-сервером: корректность запросов,
ошибки и `retry_after`, некорректные ответы и отмена запроса. PostgreSQL-тесты
проверяют повторы updates, откат checkpoint, изоляцию bot ID, устаревший offset
и перезапуск после коммита до подтверждения Telegram. CI и smoke-проверка
принудительно выключают polling; для них не нужны реальные Telegram-секреты.

## PostgreSQL в GitHub Actions

В Settings → Secrets and variables → Actions задайте следующие **Variables**:

| Имя | Назначение |
| --- | --- |
| `PGHOST` | Адрес service-контейнера с точки зрения раннера: `127.0.0.1` |
| `PGPORT` | Свободный порт раннера, на который CI публикует PostgreSQL |
| `PGDATABASE` | Имя отдельной тестовой базы |
| `PGUSER` | Имя роли тестовой базы |
| `PGSSLMODE` | `disable` для локального service-контейнера без TLS |

В **Secrets** добавьте `PGPASSWORD` — пароль этой тестовой роли. Пароль
передаётся через окружение; его не следует хранить в Variables, YAML или URL.
Workflow создаёт временный PostgreSQL с заданными именами и паролем, используя
SCRAM-SHA-256 вместо `trust`. Этот CI не подключается к рабочей базе.
Все перечисленные значения обязательны; фиксированных учётных данных и
запасного пароля в workflow нет. PR из fork не получает repository secrets,
поэтому для него эти проверки БД недоступны без отдельной настройки.

Контейнерная проверка использует второй, отдельный PostgreSQL в сети Compose
с теми же `PGUSER`, `PGDATABASE`, `PGPASSWORD`, `PGSSLMODE`. Внутри этой сети
приложение получает `PGHOST=db`, `PGPORT=5432` — адрес сервиса, а не адрес
порта раннера. Параметры подключения передаются приложению через окружение.

## Контейнер для разработки

```sh
VCS_REF=$(git rev-parse HEAD) docker compose -f compose.dev.yaml up --build --wait
docker compose -f compose.dev.yaml exec app /payplump healthcheck
docker compose -f compose.dev.yaml logs app
docker compose -f compose.dev.yaml stop app
docker compose -f compose.dev.yaml up -d --wait
```

В текущем облачном окружении сборщику нужны сетевой прокси и доверенный
CA bundle хоста. Их можно передать только на время сборки, не сохраняя
в образе или исходниках:

```sh
docker build --network=host \
  --add-host "proxy:$(getent ahostsv4 proxy | awk 'NR == 1 {print $1}')" \
  --build-arg HTTP_PROXY --build-arg HTTPS_PROXY --build-arg NO_PROXY \
  --secret "id=build_ca,src=$SSL_CERT_FILE" \
  --build-arg VCS_REF="$(git rev-parse HEAD)" -t payplump:dev .
docker compose -f compose.dev.yaml up --no-build --wait
```

Проверки TLS и `go.sum` при этом включены. За пределами этого окружения
обычно достаточно стандартной команды Compose выше. `DOCKER_CONFIG` из
раздела облачной настройки нужен, поскольку домашний каталог здесь read-only.

Локальная сборка использует многоэтапный Dockerfile: Go с `CGO_ENABLED=0`,
финальная база `gcr.io/distroless/static-debian13:nonroot`. Обе базы закреплены
по digest; миграции встроены в бинарник, сертификаты и tzdata входят в базу.
Сервис работает от UID
65532 с read-only файловой системой. Docker healthcheck вызывает подкоманду
самого бинарника. HTTP опубликован только на `127.0.0.1:8080`, PostgreSQL —
на `127.0.0.1:15432`. Переменные `PAYPLUMP_HTTP_PORT` и `PAYPLUMP_DB_PORT`
позволяют выбрать другие локальные порты; задавайте их одинаково во всех
командах Compose. Остановите ранее запущенную тестовую БД или выберите
другой порт, чтобы избежать конфликта.

`compose.dev.yaml` предназначен только для разработки: локальный тег
`payplump:dev`, без реестра и рабочих интеграций. PostgreSQL требует пароль
из окружения; `trust` не используется. Данные
сохраняются в volume; `docker compose -f compose.dev.yaml down` удаляет
контейнеры, но сохраняет volume. Добавление `--volumes` удаляет данные.
Новые значения `POSTGRES_*` применяются при инициализации пустого volume.
Если volume создан раньше, роль и пароль нужно обновить в существующей БД
либо использовать отдельный новый Compose project/volume; изменение `.env`
не меняет пароль в уже созданной базе.

Лимиты 128 MiB для приложения, 256 MiB для БД, `GOMEMLIMIT=96MiB`, 1 CPU
и ротация логов ограничивают локальное окружение. Это начальные значения
для разработки; они ещё не проверены на бизнес-нагрузке и не являются
рекомендацией для VPS. Рабочий выпуск должен использовать digest готового
образа, а не локальную сборку или тег `dev`. Публикация в реестр и развёртывание
Komodo здесь не выполняются.

## План реализации

Пошаговый план с чекбоксами, выполненной основой, зависимостями этапов и
покрытием критериев приёмки — в [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md).
Текущий этап — приём личного `/start`; далее нужны подтверждённые контракты
Invoice Ninja / S-UI и исполнители долговечных заданий. Проверку API на чтение
можно готовить параллельно. Состояние пунктов обновляется в соответствующих PR.

Таблицы `operations` сейчас хранят задания, но worker ещё не реализован.
Транзакционная регистрация предотвращает дубли в БД; идемпотентность внешних
API и защита от неопределённого результата запроса относятся к следующему этапу.
Рабочие секреты, адреса и параметры интеграций понадобятся при их подключении.
